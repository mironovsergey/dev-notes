# Разбор задачи «Железные дороги»

[← К содержанию спринта](README.md)

Финальная задача B шестого спринта. Разбор вынесен отдельно: прием, на котором
она построена, из условия не виден совершенно, а прямолинейные решения не
проходят по времени.

---

## Условие

В стране `n` городов с номерами от 1 до `n`. Между **каждой** парой городов
проложена железная дорога одного из двух типов - `R` или `B`. Поезд едет только
по дорогам одного типа: маршрут, где встречаются оба типа, непроходим.

Двигаться можно только от города с меньшим номером к городу с большим.

Карта называется **оптимальной**, если не существует пары городов `A` и `B`
таких, что из `A` в `B` можно добраться и по дорогам типа `R`, и по дорогам
типа `B`.

Ограничение: `n ≤ 5000`.

### Формат ввода

Карта задана `n − 1` строкой. В `i`-й строке записано `n − i` символов; `j`-й
символ описывает тип дороги из города `i` в город `i + j`.

```
   n = 4

   строка 1:  B R B     дороги 1→2 (B), 1→3 (R), 1→4 (B)
   строка 2:  R B       дороги 2→3 (R), 2→4 (B)
   строка 3:  R         дорога  3→4 (R)
```

---

## Переформулировка в терминах графов

Два обстоятельства определяют все дальнейшее, и оба легко проскочить при чтении
условия.

**Первое: граф ориентированный и ациклический.** Все ребра ведут от меньшего
номера к большему, поэтому вернуться назад невозможно и цикла быть не может.
Нумерация вершин сама по себе является
[топологическим порядком](dfs.md#634-топологическая-сортировка).

**Второе: граф полный.** Дорога есть между **каждой** парой городов. Это не
«разреженный граф с редкими связями», а полный граф на `n` вершинах, ребра
которого раскрашены в два цвета. Отсюда сразу следует
`|E| = n·(n − 1) / 2`, то есть при `n = 5000` ребер около `12,5` миллиона.

Итак, есть два графа на одном множестве вершин:

- `G_R` - только красные ребра;
- `G_B` - только синие ребра.

Каждое ребро полного графа принадлежит ровно одному из них.

**Вопрос задачи:** существует ли пара `(i, j)`, для которой `j` достижима из `i`
и в `G_R`, и в `G_B`?

```
   Пример: n = 4, карта  BRB | RB | R

   G_R:  1──→3──→4        G_B:  1──→2──→4
             ↑                  └───────↑
             2                  1──→4

   В G_R: 1 → 3 → 4, значит, из 1 достижима 4.
   В G_B: 1 → 4 напрямую.
   Пара (1, 4) достижима обоими цветами → карта НЕ оптимальна.
```

Обратите внимание: у любой пары `i < j` есть **прямое** ребро какого-то цвета,
поэтому одним цветом `j` из `i` достижима всегда. Вопрос лишь в том, не
находится ли путь еще и вторым цветом.

---

## Почему прямолинейное решение не проходит

Напрашивается вычислить достижимость и сравнить.

**Обход из каждой вершины.** Запустить [DFS](dfs.md#631-алгоритм-dfs) или
[BFS](bfs.md#651-алгоритм-bfs) из каждой вершины в каждом графе. Один обход
стоит `O(|V| + |E|)`, всего обходов `2n`:

```
   2 · 5000 · (5000 + 12 500 000) ≈ 1,25 · 10¹¹ операций
```

Безнадежно.

**Хранение множеств достижимости.** Для каждой вершины хранить множество
достижимых из нее. Множеств `n`, каждое размера до `n`, - это `n² = 25` миллионов
элементов на граф. По времени вычисление тоже квадратично-кубическое, если
объединять множества наивно.

Битовые маски снимают проблему: `n²/32 ≈ 780` тысяч машинных слов на граф. Такое
решение существует и работает, но требует ручной работы с битами.

Требуется что-то, дающее ответ про пару за `O(1)` без хранения множеств.

---

## Решение через времена входа-выхода

Ровно это и дает прием из
[раздела 6.3.3](dfs.md#633-поиск-цикла-и-времена-входа-выхода). Напомню его.

При обходе в глубину для каждой вершины записываются момент входа `entry[v]` и
момент выхода `leave[v]`. Интервалы `[entry[v], leave[v]]` образуют правильную
скобочную структуру: два интервала либо не пересекаются, либо один вложен в
другой.

```
   1: [1 ................................ 12]
   3:    [2 ................ 9]
   4:       [3 ...... 6]
   7:          [4 . 5]
   6:                 [7 . 8]
   2:                          [10 ... 11]
```

Отсюда проверка отношения «предок - потомок» за `O(1)`:

```
   j - потомок i в дереве обхода  ⟺  entry[i] < entry[j]  и  leave[i] > leave[j]
```

Алгоритм решения:

1. построить `G_R` и `G_B`;
2. вычислить `entry` и `leave` в каждом из них;
3. перебрать все пары `i < j` и проверить, является ли `j` потомком `i`
   **одновременно** в обоих лесах обхода;
4. если такая пара нашлась - карта не оптимальна.

```js
/**
 * Вычисляет времена входа и выхода для всех вершин графа.
 *
 * Вершины перебираются во внешнем цикле по возрастанию номера - это
 * существенно: нумерация является топологическим порядком графа.
 *
 * Время: O(|V| + |E|). Память: O(|V|).
 *
 * @param {number} n Количество вершин.
 * @param {number[][]} adjacency Списки смежности.
 * @returns {{entry: number[], leave: number[]}} Времена входа и выхода.
 */
function computeTimings(n, adjacency) {
  const visited = new Uint8Array(n + 1);
  const entry = new Int32Array(n + 1);
  const leave = new Int32Array(n + 1);
  let time = 0;

  const visit = (start) => {
    visited[start] = 1;
    entry[start] = ++time;

    for (const next of adjacency[start]) {
      if (!visited[next]) {
        visit(next);
      }
    }

    leave[start] = ++time;
  };

  for (let v = 1; v <= n; v++) {
    if (!visited[v]) {
      visit(v);
    }
  }

  return { entry, leave };
}
```

Перебор пар стоит `O(n²) = 25` миллионов проверок - это проходит.

### Чего эта проверка на самом деле **не** означает

Здесь и находится место, в котором проще всего убедить себя в неверном.

Соблазнительно считать, что «`j` - потомок `i` в лесу обхода» равносильно
«`i` достигает `j`». **Это не так.** Верна лишь одна импликация:

```
   j - потомок i   ⟹   i достигает j          верно всегда
   i достигает j   ⟹   j - потомок i          НЕВЕРНО
```

Контрпример: ребра `1→3`, `2→3`, `3→4`.

```
   Обход из 1: 1 → 3 → 4.   entry: 1→1, 3→2, 4→3   leave: 4→4, 3→5, 1→6
   Обход из 2: 3 уже черная. entry: 2→7            leave: 2→8

   Вершина 2 достигает 4 (через 3), но интервал [7, 8]
   не содержит интервал [3, 4] - по проверке 4 не потомок 2.
```

Я прогнал эту проверку на случайных картах: из **1 448 384** проверенных пар
результат «потомок» разошелся с настоящей достижимостью в **232 555** случаях,
то есть в 16 %. Проверка систематически **недооценивает** достижимость.

### Почему решение при этом верное

Алгоритм отвечает не на вопрос «какие пары достижимы», а на вопрос «существует
ли хоть одна плохая пара». И достаточно, чтобы выполнялось более слабое
утверждение:

> Если существует пара, достижимая обоими цветами, то существует и пара,
> являющаяся парой «предок - потомок» в обоих лесах обхода.

Это не та же самая пара - она может быть другой. В примере выше, если дополнить
карту до полной, нарушение действительно обнаруживается, но на паре `(1, 4)`, а
не `(2, 4)`.

Я проверил утверждение **исчерпывающе** для малых `n` - перебором всех
возможных карт - и на случайных картах большего размера:

| Проверка | Объем | Расхождений |
| --- | --- | --- |
| Все карты для `n = 2…5` | 1098 карт | 0 |
| Все карты для `n = 2…6` (с критерием ниже) | 33 866 карт | 0 |
| Случайные карты, `n ≤ 8` | 280 000 карт | 0 |

Существенную роль играет то, что внешний цикл обхода перебирает вершины **по
возрастанию номера**. Нумерация здесь - топологический порядок, и обход,
начатый из вершины `i`, не может «провалиться» в вершины с меньшими номерами.
Если запускать обходы в произвольном порядке, прием перестает работать.

### Стоимость

Замер на предельных данных `n = 5000` (вход 12,5 МБ, ответ `YES`, то есть
перебор пар выполняется полностью):

```
   построение двух списков смежности   227 мс,  141 МБ
   все решение целиком                 394 мс
```

Больше половины времени и практически вся память уходят на построение списков
смежности для 12,5 миллиона ребер. Плюс рекурсивный обход имеет глубину до
`n = 5000` - до предела стека далеко, но запас не такой уж большой.

## Простой критерий: турнир без циклов

Теперь - решение, которое **доказывается в несколько строк** и работает вдвое
быстрее при в восемь раз меньшей памяти. Оно опирается на то, что граф полный, -
а это, повторюсь, ключевое обстоятельство условия.

### Шаг 1: от достижимости к тройкам

**Утверждение.** Карта оптимальна тогда и только тогда, когда не существует
тройки `i < k < j`, для которой ребра `i→k` и `k→j` одного цвета `c`, а ребро
`i→j` - другого цвета.

*Доказательство.* Если такая тройка есть, то `i → k → j` дает путь цвета `c`, а
прямое ребро `i→j` - путь другого цвета. Пара `(i, j)` достижима обоими цветами,
карта не оптимальна.

Обратно: пусть таких троек нет. Тогда для каждого цвета `c` верно, что путь
цвета `c` из `i` в `j` влечет `edge(i, j) = c` - это доказывается индукцией по
длине пути, а шаг индукции и есть отсутствие тройки. Значит, достижимость цветом
`c` возможна только когда прямое ребро имеет цвет `c`, а он один. ∎

Иными словами: **карта оптимальна ⟺ оба цветных графа транзитивны**.

### Шаг 2: от троек к турниру

Определим на городах отношение `≺`:

```
   для i < j:   i ≺ j,  если edge(i, j) = R
                j ≺ i,  если edge(i, j) = B
```

Каждая пара городов сравнима ровно одним способом - такое отношение называется
**турниром**.

Проверим, во что превращается условие из шага 1. Возьмем тройку `a < b < c` и
посмотрим, когда она образует цикл в `≺`:

| Цикл в `≺` | Что это значит для цветов |
| --- | --- |
| `a ≺ b ≺ c ≺ a` | `edge(a,b) = R`, `edge(b,c) = R`, `edge(a,c) = B` |
| `a ≺ c ≺ b ≺ a` | `edge(a,b) = B`, `edge(b,c) = B`, `edge(a,c) = R` |

Это в точности две запрещенные тройки из шага 1. Следовательно:

> **Карта оптимальна ⟺ турнир `≺` не содержит циклов длины 3.**

А турнир без циклов длины 3 - это в точности **транзитивный турнир**, то есть
линейный порядок.

### Шаг 3: от турнира к степеням

Остается классический факт о турнирах:

> Турнир на `n` вершинах транзитивен тогда и только тогда, когда все исходящие
> степени различны, то есть образуют набор `{0, 1, …, n − 1}`.

*Почему.* В транзитивном турнире вершины выстраиваются в цепочку, и `k`-я с
конца побеждает ровно `k` предшественниц - степени различны. Обратно: сумма всех
исходящих степеней равна числу ребер `n·(n−1)/2`, что совпадает с суммой
`0 + 1 + … + (n−1)`. Если все степени различны и лежат в `[0, n−1]`, они
обязаны быть в точности этим набором, а такой турнир единственен с точностью до
переименования - и он транзитивен. ∎

Считать исходящие степени - это один проход по входу:

```js
/**
 * Проверяет, является ли карта железных дорог оптимальной.
 *
 * Карта задает турнир: для i < j считаем i ≺ j при красной дороге и j ≺ i при
 * синей. Карта оптимальна тогда и только тогда, когда турнир транзитивен, а
 * турнир транзитивен тогда и только тогда, когда все исходящие степени
 * различны.
 *
 * Списки смежности не строятся вовсе: достаточно счетчиков степеней.
 *
 * Время: O(n²) - столько же, сколько занимает чтение входа. Память: O(n).
 *
 * @param {number} n Количество городов.
 * @param {string[]} rows Строки карты: rows[i - 1][j] - тип дороги i → i+j+1.
 * @returns {boolean} true, если карта оптимальна.
 */
function isOptimal(n, rows) {
  const outDegree = new Int32Array(n + 1);

  for (let i = 1; i < n; i++) {
    const row = rows[i - 1];

    for (let j = 0; j < row.length; j++) {
      if (row[j] === 'R') {
        outDegree[i]++;
      } else {
        outDegree[i + j + 1]++;
      }
    }
  }

  const seen = new Uint8Array(n);

  for (let v = 1; v <= n; v++) {
    if (outDegree[v] >= n || seen[outDegree[v]] === 1) {
      return false;
    }

    seen[outDegree[v]] = 1;
  }

  return true;
}
```

Проверка на тех же данных `n = 5000`:

| | Времена входа-выхода | Исходящие степени |
| --- | --- | --- |
| Время | 394 мс | **121 мс** |
| Пиковая память | 141 МБ | **17 МБ** |
| Строк кода | ~60 | ~20 |
| Рекурсия | глубина до `n` | отсутствует |
| Обоснование | требует отдельного рассуждения | доказано выше |

Критерий проверен исчерпывающим перебором всех карт для `n = 2…6` (33 866 карт)
и на 200 000 случайных карт при `n ≤ 10` - расхождений с прямым вычислением
достижимости нет.

## Структура ответа

Из связи с транзитивными турнирами следует красивое описание всех оптимальных
карт.

Транзитивный турнир на `n` помеченных вершинах - это линейный порядок, то есть
**перестановка**. Значит, оптимальные карты находятся во взаимно однозначном
соответствии с перестановками `n` элементов.

Явно: возьмем произвольную перестановку и припишем городу `i` ее значение
`rank[i]`. Раскрасим ребра правилом

```
   для i < j:   edge(i, j) = R,  если rank[i] < rank[j]
                edge(i, j) = B,  если rank[i] > rank[j]
```

Красные ребра - пары, возрастающие по обоим признакам; синие - возрастающие по
номеру и убывающие по рангу. Оба отношения транзитивны, и вместе они покрывают
все пары.

Отсюда - количество оптимальных карт:

```
   число оптимальных карт на n городах  =  n!
```

Проверка перебором всех карт:

| `n` | Всего карт `2^(n(n−1)/2)` | Оптимальных | `n!` |
| --- | --- | --- | --- |
| 3 | 8 | 6 | 6 |
| 4 | 64 | 24 | 24 |
| 5 | 1 024 | 120 | 120 |
| 6 | 32 768 | 720 | 720 |

Совпадение точное, и множества карт совпадают поэлементно: каждая оптимальная
карта порождается ровно одной перестановкой.

Доля оптимальных карт стремительно падает: при `n = 6` это уже `720 / 32768`,
около 2 %. Отсюда практический вывод про тесты: случайная карта почти наверняка
дает ответ `NO`, и проверять решение только на случайных данных бесполезно -
ветка `YES` останется непокрытой. Тесты для нее нужно строить из перестановок.

---

## Что делает задачу трудной

Три отдельных препятствия, каждое из которых само по себе неочевидно:

1. **Увидеть, что граф полный.** Из формата ввода это следует, но в глаза не
   бросается. Пока граф кажется произвольным, задача выглядит как «проверить
   достижимость для всех пар», и все решения упираются в размер.
2. **Догадаться, что достижимость считать не нужно.** Нужен ответ на вопрос о
   существовании пары, а не сама достижимость, - и это гораздо более слабое
   требование.
3. **Связать условие с временами входа-выхода.** Прием из теории дает `O(1)` на
   пару, но проверяет он отношение «предок - потомок», а не достижимость. Разрыв
   между тем, что нужно, и тем, что дает прием, - самое тонкое место разбора, и
   именно его легко принять за очевидное.

Критерий через турнир обходит все три: он не требует ни обходов, ни
достижимости, ни списков смежности - только подсчет символов во входных данных.
