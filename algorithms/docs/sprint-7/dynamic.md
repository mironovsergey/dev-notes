## 7.2 Динамическое программирование

**Динамическое программирование** (ДП) - способ решать задачу, разбивая ее на
подзадачи и **запоминая** ответы для подзадач, чтобы не вычислять одно и то же
повторно.

Название историческое и смысла не несет: «программирование» здесь означает
«составление таблицы», а не написание кода. Полезнее держать в голове рабочее
определение:

> **Динамическое программирование = перебор + таблица уже посчитанных ответов.**

Все остальное - техника.

---

### От перебора к динамике

Разберем переход на числах Фибоначчи. Задача проста, и это позволяет
сосредоточиться на самом приеме.

```
   F(0) = 0
   F(1) = 1
   F(n) = F(n − 1) + F(n − 2)
```

Определение переводится в код дословно:

```js
/**
 * Возвращает n-е число Фибоначчи прямой рекурсией по определению.
 *
 * Время: O(φⁿ), где φ ≈ 1,618. Память: O(n) на кадры стека вызовов.
 *
 * @param {number} n Номер числа, n >= 0.
 * @returns {number} Значение F(n).
 */
function fibNaive(n) {
  if (n <= 1) {
    return n;
  }

  return fibNaive(n - 1) + fibNaive(n - 2);
}
```

Код верный, но безнадежно медленный. Замер:

| `n` | вызовов функции | время |
| --- | --- | --- |
| 20 | 21 891 | 1 мс |
| 30 | 2 692 537 | 10 мс |
| 35 | 29 860 703 | 77 мс |
| 40 | 331 160 281 | 877 мс |

При `n = 50` это заняло бы уже около двух минут, при `n = 60` - больше двух
часов.

#### Где именно теряется время

Нарисуем дерево вызовов для `F(5)`:

```
                        F(5)
                   ╱          ╲
               F(4)            F(3)
             ╱      ╲         ╱     ╲
         F(3)       F(2)    F(2)    F(1)
        ╱    ╲     ╱   ╲   ╱   ╲
     F(2)   F(1) F(1) F(0) F(1) F(0)
    ╱   ╲
  F(1)  F(0)
```

`F(3)` вычисляется дважды, `F(2)` - трижды, `F(1)` - пять раз. И каждое
повторное вычисление разворачивает **все свое поддерево заново**.

Замер на `n = 30`:

```
   всего вызовов                     2 692 537
   различных подзадач                       31
   сколько раз вычисляется F(1)        832 040
```

Тридцать одна различная подзадача - и почти три миллиона вычислений. Вот все
содержание динамического программирования в одной строке.

#### Первое решение: записывать ответы

Добавим блокнот: перед вычислением смотрим, не считали ли мы это раньше; после
вычисления записываем.

```js
/**
 * Возвращает n-е число Фибоначчи с запоминанием вычисленных значений.
 *
 * Каждая подзадача вычисляется ровно один раз: повторный вызов находит готовый
 * ответ в таблице.
 *
 * Время: O(n). Память: O(n).
 *
 * @param {number} n Номер числа, n >= 0.
 * @param {Map<number, number>} memo Таблица вычисленных значений.
 * @returns {number} Значение F(n).
 */
function fibMemo(n, memo = new Map()) {
  if (n <= 1) {
    return n;
  }

  if (memo.has(n)) {
    return memo.get(n);
  }

  const result = fibMemo(n - 1, memo) + fibMemo(n - 2, memo);

  memo.set(n, result);

  return result;
}
```

Изменились три строки, а сложность упала с `O(φⁿ)` до `O(n)`. Причина ровно та,
что видна в таблице выше: подзадач всего `n + 1`, каждая теперь считается один
раз.

Этот прием - запоминание результатов функции - называется **мемоизацией**.

---

### Два условия применимости

Динамическое программирование применимо, когда выполняются оба условия.

#### 1. Оптимальная подструктура

Ответ для задачи выражается через ответы для **меньших задач того же вида**.

Для Фибоначчи это буквально записано в определении. В содержательных задачах
это утверждение приходится доказывать: например, для кратчайшего пути оно
звучит так - любой участок кратчайшего пути сам является кратчайшим путем между
своими концами. Если бы это было не так, участок можно было бы заменить более
коротким и улучшить весь путь.

Свойство есть не всегда. Для **самого длинного простого пути** в графе оно не
выполняется: участок самого длинного пути не обязан быть самым длинным путем
между своими концами, и динамика здесь не строится.

#### 2. Перекрывающиеся подзадачи

Одни и те же подзадачи встречаются многократно. Именно это делает запоминание
выгодным.

Сравним с сортировкой слиянием:

| | Фибоначчи | [Сортировка слиянием](../sprint-3/sorting.md#324-сортировка-слиянием) |
| --- | --- | --- |
| Оптимальная подструктура | есть | есть |
| Перекрывающиеся подзадачи | **есть** | нет |
| Нужно ли запоминать | да | **бессмысленно** |

Сортировка слиянием делит массив на две **непересекающиеся** половины. Одна и
та же подзадача не встречается дважды, запоминать нечего. Это «разделяй и
властвуй», а не динамика.

Различие удобно проверять по дереву рекурсии: если в нем есть **повторяющиеся
узлы** - это динамика; если все узлы различны - «разделяй и властвуй».

#### Как это соотносится с жадностью

| | Жадный алгоритм | Динамика | Полный перебор |
| --- | --- | --- | --- |
| Оптимальная подструктура | нужна | нужна | не нужна |
| [Свойство жадного выбора](greedy.md#два-условия-применимости) | **нужно** | не нужно | не нужно |
| Что делает с вариантами первого шага | **угадывает** один | перебирает все, запоминая | перебирает все |
| Типичное время | `O(n·log n)` | `O(n·W)`, `O(n·m)` | `O(2ⁿ)` |

Динамика - компромисс: она честно перебирает все варианты, как полный перебор,
но не платит за повторы. Поэтому там, где жадность ломается - например, в
[целочисленном рюкзаке](greedy.md#7122-задача-о-рюкзаке-с-целыми-элементами), -
ответ дает именно динамика.

### Мемоизация и табуляция

Одну и ту же динамику записывают двумя способами.

**Мемоизация (сверху вниз).** Обычная рекурсия по определению задачи плюс
таблица. Вычисляются только те подзадачи, которые реально нужны.

**Табуляция (снизу вверх).** Цикл, заполняющий таблицу от базовых случаев к
искомому. Рекурсии нет вовсе.

```js
/**
 * Возвращает n-е число Фибоначчи табличным способом.
 *
 * Таблица заполняется от базовых значений к искомому, поэтому к моменту
 * вычисления dp[i] значения dp[i-1] и dp[i-2] уже готовы.
 *
 * Время: O(n). Память: O(n).
 *
 * @param {number} n Номер числа, n >= 0.
 * @returns {number} Значение F(n).
 */
function fibTable(n) {
  if (n <= 1) {
    return n;
  }

  const dp = new Array(n + 1);

  dp[0] = 0;
  dp[1] = 1;

  for (let i = 2; i <= n; i++) {
    dp[i] = dp[i - 1] + dp[i - 2];
  }

  return dp[n];
}
```

| | Мемоизация | Табуляция |
| --- | --- | --- |
| Форма записи | рекурсия | цикл |
| Порядок вычислений | определяется сам | **задаете вы** |
| Вычисляет подзадачи | только нужные | все |
| Риск переполнения стека | **есть** | нет |
| Накладные расходы | вызовы функций, хеш-таблица | только массив |
| Проще писать | когда переходы запутанные | в большинстве случаев |
| Экономия памяти скользящим окном | невозможна | **возможна** |

**Практический совет.** Начинайте с мемоизации: она пишется механически из
рекурсивного определения, и в ней труднее ошибиться. Получив работающее
решение, переписывайте в таблицу - ради скорости, отсутствия рекурсии и
[экономии памяти](#экономия-памяти).

Отдельно про стек: глубина рекурсии при мемоизации равна глубине зависимостей,
и для `n = 10⁵` она
[переполнит стек вызовов](../sprint-2/stack-and-queue.md#применение-стек-вызовов).
Это частая причина, по которой мемоизация не проходит там, где таблица
проходит.

### Рецепт из пяти шагов

Дальше все задачи разбираются по одной и той же схеме. Она и есть главный
практический результат этого раздела - если что-то одно уносить из спринта, то
это.

> **1. Состояние.** Что означает ячейка таблицы? Сформулируйте словами, целым
> предложением: «`dp[i]` - это …». Пока предложение не сформулировано, писать
> код рано.
>
> **2. База.** Какие состояния известны сразу, без вычислений?
>
> **3. Переход.** Как выразить состояние через **меньшие** состояния? Обычно это
> вопрос «каким был последний шаг?» с перебором всех вариантов.
>
> **4. Порядок.** В каком порядке заполнять таблицу, чтобы к моменту вычисления
> состояния все нужные ему состояния были готовы?
>
> **5. Ответ.** В какой ячейке лежит результат?

Прогоним рецепт на Фибоначчи - задача тривиальна, зато видна вся схема:

1. **Состояние:** `dp[i]` - `i`-е число Фибоначчи.
2. **База:** `dp[0] = 0`, `dp[1] = 1`.
3. **Переход:** `dp[i] = dp[i − 1] + dp[i − 2]`.
4. **Порядок:** по возрастанию `i` - оба нужных значения меньше `i`.
5. **Ответ:** `dp[n]`.

Самый важный шаг - первый. Большинство трудностей с динамикой сводится к тому,
что состояние сформулировано нечетко: «`dp[i]` - что-то про первые `i`
элементов». Пока не сказано **что именно**, переход выписать невозможно.

Второй по важности - третий шаг, и к нему есть надежный подход: спросить **«каким
был последний шаг?»** и перебрать все возможные ответы. Каждый вариант последнего
шага отсылает к меньшему состоянию.

### 7.2.1 Задача про лестницу

**Условие.** Лестница из `n` ступенек. За один прыжок можно подняться на 1 или
2 ступеньки. Сколькими способами можно подняться с земли на `n`-ю ступеньку?

#### Применяем рецепт

**1. Состояние.** `dp[i]` - количество способов добраться до ступеньки `i`.

**2. База.** `dp[0] = 1` - на землю можно попасть ровно одним способом:
никуда не прыгать. Это соглашение часто вызывает вопросы, но оно правильное:
пустой способ - тоже способ, и без него формула не сойдется.

**3. Переход.** Спросим: каким был **последний** прыжок? Вариантов ровно два -
с ступеньки `i − 1` или с ступеньки `i − 2`. Эти множества способов не
пересекаются (последний прыжок различается) и покрывают все. Значит:

```
   dp[i] = dp[i − 1] + dp[i − 2]
```

**4. Порядок.** По возрастанию `i`: оба слагаемых меньше `i`.

**5. Ответ.** `dp[n]`.

```js
/**
 * Возвращает количество способов подняться на n-ю ступеньку прыжками
 * на 1 или 2 ступеньки.
 *
 * Состояние dp[i] - количество способов добраться до ступеньки i. Переход
 * разбирает случаи по последнему прыжку: он был либо с i-1, либо с i-2,
 * и эти множества способов не пересекаются.
 *
 * Время: O(n). Память: O(n).
 *
 * @param {number} n Номер целевой ступеньки, n >= 0.
 * @returns {number} Количество способов.
 */
function countWays(n) {
  const dp = new Array(n + 1).fill(0);

  // На землю можно попасть единственным способом - не прыгая
  dp[0] = 1;

  for (let i = 1; i <= n; i++) {
    dp[i] = dp[i - 1] + (i >= 2 ? dp[i - 2] : 0);
  }

  return dp[n];
}
```

#### Трассировка для `n = 6`

| `i` | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `dp[i]` | 1 | 1 | 2 | 3 | 5 | 8 | **13** |

Получились числа Фибоначчи - и это не совпадение: рекуррентное соотношение то
же самое, отличается только база.

#### Вариант: прыжки до `k` ступенек

Если за прыжок можно подняться на любое расстояние от 1 до `k`, меняется только
шаг 3: последний прыжок мог быть с любой из `k` предыдущих ступенек.

```
   dp[i] = dp[i − 1] + dp[i − 2] + … + dp[i − k]
```

```js
/**
 * Возвращает количество способов подняться на n-ю ступеньку прыжками
 * на расстояние от 1 до k, по модулю заданного числа.
 *
 * Взятие остатка на каждом шаге обязательно: количество способов растет
 * экспоненциально и уже при небольших n выходит за пределы точного
 * представления целых чисел.
 *
 * Время: O(n·k). Память: O(n).
 *
 * @param {number} n Номер целевой ступеньки.
 * @param {number} k Наибольшая длина прыжка.
 * @param {number} modulo Модуль, по которому берется ответ.
 * @returns {number} Количество способов по модулю modulo.
 */
function countWaysUpToK(n, k, modulo = 1_000_000_007) {
  const dp = new Array(n + 1).fill(0);

  dp[0] = 1;

  for (let i = 1; i <= n; i++) {
    for (let jump = 1; jump <= Math.min(k, i); jump++) {
      dp[i] = (dp[i] + dp[i - jump]) % modulo;
    }
  }

  return dp[n];
}
```

Сложность выросла до `O(n·k)`. Ее можно вернуть к `O(n)`, заметив, что сумма
`k` последних значений пересчитывается через предыдущую сумму - прибавить одно
значение, вычесть выпавшее. Это тот же прием
[скользящего окна](../sprint-2/two-pointers.md#схема-2-скользящее-окно).

#### Вариант: запрещенные ступеньки

Если на некоторые ступеньки наступать нельзя, добавляется одна строка:

```js
if (isForbidden[i]) {
  dp[i] = 0;
  continue;
}
```

Ноль означает «сюда нельзя попасть», и это значение автоматически исключает
ступеньку из всех дальнейших сумм. Отдельной логики не требуется.

#### Вариант: минимальная стоимость

Если за посещение ступеньки `i` платят `cost[i]`, и нужен самый дешевый подъем,
меняются только шаги 1 и 3:

1. **Состояние:** `dp[i]` - минимальная стоимость подъема на ступеньку `i`.
3. **Переход:** `dp[i] = cost[i] + min(dp[i − 1], dp[i − 2])`.

Схема та же, задача другая. В этом и польза рецепта: он превращает «придумать
алгоритм» в «заполнить пять пунктов».

> **Сумма или минимум?** Если задача спрашивает «сколькими способами» -
> варианты **складываются**. Если «как лучше всего» - берется **минимум или
> максимум**. Это первое, что стоит определить, читая условие: от ответа
> зависит и вид перехода, и значение базы (`0` против `Infinity`).

### Восстановление ответа

Таблица дает **значение** оптимума. Часто нужен и сам ответ: не «максимальная
стоимость», а «какие предметы взять».

Есть два способа.

**Способ 1: пройти по таблице назад.** Стоя в конечном состоянии, определяем,
из какого состояния мы в него пришли, - тем же перебором вариантов, что и в
переходе. Дополнительной памяти не требуется.

```js
/**
 * Восстанавливает самый дешевый маршрут подъема по лестнице.
 *
 * Проход идет от конца к началу: в каждом состоянии проверяется, какой из
 * вариантов перехода дал записанное значение. Дополнительная таблица
 * предшественников не нужна - вариант определяется повторной проверкой.
 *
 * Время: O(n). Память: O(длины маршрута).
 *
 * @param {number[]} dp Таблица минимальных стоимостей.
 * @param {number[]} cost Стоимости ступенек.
 * @param {number} n Номер целевой ступеньки.
 * @returns {number[]} Номера ступенек маршрута от начала к концу.
 */
function restorePath(dp, cost, n) {
  const path = [];
  let i = n;

  while (i > 0) {
    path.push(i);
    i = i >= 2 && dp[i - 2] < dp[i - 1] ? i - 2 : i - 1;
  }

  path.push(0);

  return path.reverse();
}
```

**Способ 2: хранить выбор.** Параллельно с `dp` заполнять массив `from`, в
котором записано, из какого состояния получено текущее. Требует `O(размера
таблицы)` дополнительной памяти, но восстановление становится тривиальным.

Первый способ предпочтительнее, когда таблица большая: он ничего не хранит.
Второй - когда переход сложный и повторно вычислять его дорого или неудобно.

### Экономия памяти

Часто для вычисления очередного состояния нужны не все предыдущие, а лишь
несколько последних. Тогда таблицу целиком хранить незачем.

Для лестницы нужны ровно два предыдущих значения:

```js
/**
 * Возвращает количество способов подняться на n-ю ступеньку,
 * храня только два последних значения.
 *
 * Время: O(n). Память: O(1).
 *
 * @param {number} n Номер целевой ступеньки, n >= 0.
 * @returns {number} Количество способов.
 */
function countWaysConstantMemory(n) {
  let previous = 1; // dp[i - 1], в начале это dp[0]
  let beforePrevious = 0; // dp[i - 2]

  for (let i = 1; i <= n; i++) {
    const current = previous + beforePrevious;

    beforePrevious = previous;
    previous = current;
  }

  return previous;
}
```

Тот же прием в двумерных задачах называется **скользящей строкой**: если
`dp[i][j]` зависит только от строки `i − 1`, хватает двух строк вместо всей
таблицы - память падает с `O(n·m)` до `O(m)`. Подробнее - в разборе
[рюкзака](knapsack.md#экономия-памяти-до-ow).

**Важное ограничение.** Свернув таблицу, вы теряете возможность
[восстановить ответ](#восстановление-ответа): промежуточных состояний больше
нет. Если нужен не только оптимум, но и сам набор, таблицу приходится хранить
целиком.

---

### Типичные ошибки

**Состояние сформулировано нечетко.** «`dp[i]` - что-то про первые `i`
элементов» - не формулировка. Должно быть предложение, из которого однозначно
понятно, какое число лежит в ячейке. Если переход не выписывается, почти всегда
виновато состояние: его нужно уточнить или добавить измерение.

**База не покрывает всех случаев.** Классика - забыть `dp[0]` или задать его
неверно. Проверка простая: подставьте в переход самое маленькое `i` и
убедитесь, что все нужные ячейки уже заданы.

**Неверный порядок заполнения.** Если `dp[i]` вычисляется раньше `dp[i − 1]`,
он прочитает не заполненную ячейку. В одномерном случае это заметно сразу, в
двумерном - далеко не всегда.

**Переход учитывает вариант дважды.** При подсчете количества способов варианты
должны **не пересекаться**. Разбор по последнему шагу это гарантирует;
разбор «по какому-нибудь шагу» - нет. Так, при подсчете способов размена монет
перебор в порядке «сначала сумма, потом монеты» считает `1 + 2` и `2 + 1` как
разные варианты, а «сначала монеты, потом сумма» - как один.

**Переполнение при подсчете количеств.** Количество способов растет
экспоненциально. Если в условии сказано «выведите ответ по модулю» - это не
формальность, а указание, что без модуля числа не поместятся.

**Мемоизация переполняет стек.** Глубина рекурсии равна глубине зависимостей.
Для `n = 10⁵` нужна таблица, а не рекурсия.

**Динамика там, где хватает жадности, и наоборот.** Жадный алгоритм проще и
быстрее, но требует доказательства. Динамика медленнее, но доказательства
требует только оптимальная подструктура. Если жадность не удается ни доказать,
ни сломать за несколько минут - берите динамику.
