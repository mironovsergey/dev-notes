# 1 Система типов

[← К содержанию](../README.md)

TypeScript - это JavaScript со статической системой типов: типы проверяются до
запуска и полностью исчезают из результата компиляции. Программа на TypeScript
ведет себя в рантайме ровно так же, как ее JavaScript-версия. Система типов не
добавляет проверок в работающий код - она только отвергает часть программ на
этапе компиляции.

Три свойства системы типов определяют все остальное в конспекте:

- она **структурная**: совместимость типов определяется составом членов, а не
  именем ([1.1](#11-структурная-типизация-и-совместимость-типов));
- она **стираемая**: в JavaScript от типов не остается ничего
  ([1.7](#17-стирание-типов-что-остается-в-javascript)), поэтому проверка
  данных, пришедших извне, целиком лежит на программисте;
- она **намеренно неполна**: `any`, утверждения типов и некоторые правила
  совместимости функций пропускают программы, которые падают в рантайме. Это
  плата за совместимость с существующим JavaScript.

Модель, полезная на протяжении всего конспекта: **тип - это множество
значений**. `string` - множество всех строк, `'admin'` - множество из одной
строки, `never` - пустое множество, `unknown` - множество всех значений вообще.
Присваивание значения типа `S` переменной типа `T` допустимо, когда `S ⊆ T`.
Объединение `|` и пересечение `&` - это в точности
[операции над множествами](../../mathematics/docs/sprint-1/sets.md#122-операции-и-законы-алгебры-множеств).

## 1.1 Структурная типизация и совместимость типов

**Структурная типизация** - правило совместимости, при котором тип `S`
совместим с типом `T`, если `S` содержит все члены `T` с совместимыми типами;
имя типа и место его объявления значения не имеют.

Противоположный подход - **номинативная** типизация (Java, C#, Rust, Swift):
там два класса с одинаковым набором полей - разные типы, пока один не объявлен
наследником другого.

### Почему структурная

TypeScript типизирует существующий JavaScript, в котором объекты возникают из
литералов, `JSON.parse`, деструктуризации и чужих библиотек и не несут никакой
«метки типа». Номинативная система потребовала бы явно объявлять
принадлежность каждого объекта к типу, а для объекта, пришедшего из сети, это
невозможно. Структурная система принимает объект, если у него есть нужные
свойства, - ровно так, как проверяет его сам JavaScript-код.

### Как устроена проверка

```ts
interface Point {
  x: number;
  y: number;
}

interface Coordinate {
  x: number;
  y: number;
}

const p: Point = { x: 10, y: 20 };
// Совместимы: наборы членов совпадают, имена типов не сравниваются.
const c: Coordinate = p;

interface Point3D {
  x: number;
  y: number;
  z: number;
}

const p3: Point3D = { x: 1, y: 2, z: 3 };
// Допустимо: у Point3D есть все, что требует Point. Лишнее свойство z не мешает.
const p2: Point = p3;

// const back: Point3D = p2;
// Ошибка TS2741: Property 'z' is missing in type 'Point' but required in type 'Point3D'.
```

Правило работает в одну сторону: тип с большим числом свойств присваивается
типу с меньшим, но не наоборот. В терминах множеств `Point3D ⊆ Point`: каждое
значение с полями `x`, `y`, `z` заведомо имеет поля `x` и `y`.

То же правило распространяется на параметры функций. Функция объявляет только
то, что ей нужно, и принимает любой объект, у которого это есть:

```ts
function greet(entity: { name: string }): string {
  return `Hello, ${entity.name}`;
}

const user = { name: 'Ann', email: 'ann@example.com', age: 30 };
greet(user); // допустимо: name есть, остальное игнорируется
```

| Присваивание | Результат | Причина |
| --- | --- | --- |
| `Point3D → Point` | допустимо | лишнее свойство не нарушает контракт |
| `Point → Point3D` | ошибка TS2741 | отсутствует обязательное свойство `z` |
| литерал `{ x, y, z } → Point` | ошибка TS2353 | проверка избыточных свойств для свежего литерала |

Третья строка выглядит противоречием: только что лишнее свойство «не мешало».
Это отдельная проверка, а не правило совместимости: объектный литерал,
записанный прямо в месте присваивания, с лишним свойством почти всегда означает
опечатку в имени, и компилятор сообщает о ней. Как только тот же объект попадает
в переменную, проверка не применяется. Подробно - в
[4.2](object-types.md#42-проверка-избыточных-свойств-и-свежесть-объектного-литерала).

### Классы тоже сравниваются по структуре

Структурное правило действует и для классов - со всеми последствиями:

```ts
class Celsius {
  constructor(public value: number) {}
}

class Fahrenheit {
  constructor(public value: number) {}
}

// Компилируется: у обоих классов одно поле value: number.
const boiling: Celsius = new Fahrenheit(212);
```

Компилятор не защищает от смешения единиц измерения, идентификаторов разных
сущностей и любых других типов с одинаковой формой. Способов сделать тип
«именным» два:

- **приватный член**. Типы с `private` или `protected` членами совместимы,
  только если член унаследован от одного и того же объявления, - это
  единственное место, где TypeScript сравнивает по происхождению
  ([6.2](classes.md#62-модификаторы-доступа-public-protected-private-readonly-private-против-private));
- **branded types** - пересечение примитива с фиктивным свойством-меткой
  ([4.4](object-types.md#44-пересечения-слияние-свойств-конфликт-свойств-и-never-branded-types)).

```ts
class Meters {
  private readonly unit = 'm';
  constructor(public value: number) {}
}

class Feet {
  private readonly unit = 'ft';
  constructor(public value: number) {}
}

// const height: Meters = new Feet(6);
// Ошибка TS2322: Type 'Feet' is not assignable to type 'Meters'.
//   Types have separate declarations of a private property 'unit'.
```

### Компромиссы

| Структурная система дает | Структурная система стоит |
| --- | --- |
| Совместимость с любым JavaScript-объектом без объявлений | Случайную совместимость типов одинаковой формы |
| Функции объявляют только нужные им свойства | Невозможность отличить `UserId` от `OrderId`, если оба - `string` |
| Отсутствие церемоний вроде `implements` для каждого объекта | Необходимость искусственных меток там, где важно происхождение |

## 1.2 Примитивные и литеральные типы

**Примитивный тип** - тип одного из семи примитивных значений JavaScript.
TypeScript не добавляет новых примитивов: целого типа, типа даты или типа
символа-строки в нем нет.

| Тип | Значения | `typeof` в рантайме | Замечание |
| --- | --- | --- | --- |
| `string` | строки | `'string'` | |
| `number` | все числа, включая `NaN` и `Infinity` | `'number'` | целого типа нет |
| `bigint` | целые произвольной длины, литерал `100n` | `'bigint'` | требует `target` не ниже ES2020 |
| `boolean` | `true`, `false` | `'boolean'` | равен объединению `true \| false` |
| `symbol` | результат `Symbol()` | `'symbol'` | |
| `null` | `null` | `'object'` | историческая ошибка JavaScript |
| `undefined` | `undefined` | `'undefined'` | |

Столбец `typeof` важен для [сужения типов](narrowing.md#72-встроенные-проверки-typeof-instanceof-in):
проверка `typeof value === 'object'` пропускает `null`, и это регулярный
источник ошибок.

```ts
const count: number = 42;
const ratio: number = 0.75;
const notANumber: number = NaN; // NaN - тоже number
const big: bigint = 9007199254740993n;
const title: string = 'TypeScript';
const done: boolean = false;
const id: symbol = Symbol('id');
const nothing: null = null;
const missing: undefined = undefined;
```

### Типы-обертки

У каждого примитива есть объект-обертка: `String`, `Number`, `Boolean`,
`Symbol`, `BigInt`. В TypeScript это отдельные объектные типы, и в аннотациях
им не место: примитив присваивается обертке, но не наоборот, а методы вроде
`toUpperCase` и так доступны у примитива через автоупаковку.

```ts
const wrapped: String = 'text'; // компилируется, но бессмысленно

// const unwrapped: string = new String('text');
// Ошибка TS2322: Type 'String' is not assignable to type 'string'.
//   'string' is a primitive, but 'String' is a wrapper object.
```

### Литеральные типы

**Литеральный тип** - тип, множество значений которого состоит из одного
конкретного значения: `'admin'`, `42`, `true`, `100n`. Каждый литеральный тип -
подмножество своего примитива: `'admin' ⊆ string`.

```ts
const answer = 42; // тип 42, а не number
const greeting = 'hello'; // тип 'hello'
const flag = true; // тип true

type Direction = 'up' | 'down' | 'left' | 'right';
type Port = 80 | 443 | 8080;
```

Литеральные типы - строительный материал для всего, что моделирует конечный
набор допустимых значений: объединений литералов вместо `enum`
([3.4](arrays-tuples-enums.md#34-enum-против-объединения-литералов-и-объекта-as-const)),
размеченных объединений
([4.3](object-types.md#43-объединения-доступ-к-общим-членам-литеральные-объединения-размеченные-объединения)),
шаблонных литеральных типов
([11.1](template-literal-types.md#111-синтаксис-и-комбинирование-объединений)).

Тип `boolean` - не отдельный примитив системы типов, а объединение двух
литеральных типов `true | false`. Поэтому `switch` по обоим значениям
компилятор считает полным:

```ts
/**
 * Возвращает 1 для true и 0 для false.
 *
 * Ветки default нет: boolean = true | false, обе ветки разобраны, и
 * компилятор не требует завершающего return.
 */
function toNumber(flag: boolean): number {
  switch (flag) {
    case true:
      return 1;
    case false:
      return 0;
  }
}
```

Если убрать ветку `case false`, появится ошибка TS2366: `Function lacks ending
return statement and return type does not include 'undefined'` - компилятор
видит, что множество `boolean` разобрано не полностью.

## 1.3 Аннотации и вывод типов, расширение литералов

**Аннотация типа** - явное указание типа после двоеточия. **Вывод типа**
(type inference) - определение типа компилятором по выражению, когда аннотации
нет.

Правило по умолчанию: аннотировать там, где компилятор вывести не может или
где тип - часть контракта; в остальных местах доверять выводу. Аннотация
локальной переменной `const count: number = 0` не добавляет безопасности - тип
и так `number`, - но добавляет шум и повод для расхождения при рефакторинге.

### Где работает вывод

| Конструкция | Пример | Выведенный тип |
| --- | --- | --- |
| Инициализатор `let` | `let n = 0` | `number` |
| Инициализатор `const` | `const greeting = 'hi'` | `'hi'` |
| Массив | `const list = [1, 2, 3]` | `number[]` |
| Массив разных типов | `const mixed = [1, 'a']` | `(string \| number)[]` |
| Объектный литерал | `const user = { name: 'Ann', age: 30 }` | `{ name: string; age: number }` |
| Возвращаемое значение | `function double(x: number) { return x * 2 }` | `number` |
| Параметр callback-а | `list.map((x) => x * 2)` | `x: number` |

Последняя строка - **контекстная типизация**: тип параметра стрелочной функции
берется из места, куда функция передается. Сигнатура `map` у `number[]`
требует callback с параметром `number`, и аннотировать `x` не нужно. Так же
получают тип обработчики событий:

```ts
document.addEventListener('click', (event) => {
  console.log(event.clientX); // event: MouseEvent, выведен из сигнатуры addEventListener
});
```

Вывод не работает для параметров функций, объявленных самостоятельно: у
компилятора нет выражения, из которого можно взять тип. Под `noImplicitAny`
(входит в `strict`) такой параметр - ошибка:

```ts
// function process(data) {
// Ошибка TS7006: Parameter 'data' implicitly has an 'any' type.
```

| Аннотировать | Доверять выводу |
| --- | --- |
| Параметры функций | Локальные переменные с инициализатором |
| Возвращаемые типы экспортируемых функций: контракт и [скорость проверки](build-and-performance.md#184-ускорение-проверки-типов-skiplibcheck-границы-include-явные-типы-экспортов-interface-против-пересечений) | Возвращаемые типы коротких внутренних функций |
| Переменные без инициализатора или с `null`/`[]` в качестве начального значения | Параметры callback-ов |
| Объектные литералы, которые должны соответствовать интерфейсу | Результаты вызовов типизированных функций |

### Расширение литералов

**Расширение** (widening) - замена литерального типа на примитивный при
выводе типа изменяемой переменной или свойства.

`const answer = 42` получает тип `42`: переменная неизменяема, других значений
в ней не будет. `let counter = 42` получает `number`: раз переменная изменяема,
компилятор предполагает, что туда запишут другое число. То же происходит со
свойствами объектного литерала - они изменяемы, поэтому расширяются:

```ts
const role = 'admin'; // 'admin'
let roleVar = 'admin'; // string
const account = { role: 'admin' }; // { role: string }

function setRole(role: 'admin' | 'user'): void {
  console.log(role);
}

setRole(role); // допустимо: 'admin' ⊆ 'admin' | 'user'

// setRole(roleVar);
// setRole(account.role);
// Ошибка TS2345: Argument of type 'string' is not assignable to parameter of type '"admin" | "user"'.
```

Это самый частый источник недоумения при работе с литеральными объединениями:
значение выглядит правильным, но его тип уже расширен до `string`. Исправления
два - аннотация в месте объявления либо `as const`, который запрещает
расширение и делает свойства `readonly`
([8.4](type-operators.md#84-as-const-литеральные-типы-readonly-на-всех-уровнях-словари-констант)):

```ts
const accountConst = { role: 'admin' } as const; // { readonly role: 'admin' }
setRole(accountConst.role); // допустимо
```

### Переменные без начального типа

Переменная, объявленная без инициализатора или с `null`/`undefined`, получает
**эволюционирующий тип**: компилятор отслеживает присваивания по потоку
управления и в каждой точке знает последний присвоенный тип. Это не нарушает
`noImplicitAny` - ошибка возникнет только при чтении до присваивания.

```ts
let value; // тип эволюционирует
value = 1; // здесь value: number
value = 'a'; // здесь value: string

const items = []; // эволюционирующий массив
items.push(1); // здесь items: number[]

let maybe = null; // здесь maybe: null
maybe = 5; // здесь maybe: number
```

Прием удобен в коротких функциях, но для экспортируемых значений и полей
объектов тип стоит задавать явно: эволюция заканчивается на границе области
видимости, и наружу уходит последнее состояние, которое легко поменять
случайно.

## 1.4 `any` и `unknown`

**`any`** - тип, отключающий проверку: в него присваивается что угодно, он
присваивается куда угодно, обращение к любому его члену и вызов с любыми
аргументами компилируются без проверки.

`any` существует для двух задач: постепенной миграции JavaScript-кода и
взаимодействия с кодом, который типизировать невозможно. За пределами этих
задач `any` - не тип, а отказ от типизации в отдельно взятом месте.

```ts
let anything: any = 42;
anything = 'text';
anything.foo.bar; // компилируется, в рантайме - TypeError
const n: number = anything; // any присваивается куда угодно
```

Опасность `any` в его заразности: результат любого выражения с `any` - снова
`any`, и один такой источник распространяется по цепочке вызовов, не вызывая
ни одной ошибки. Источники `any`, которые появляются сами, без объявления:

| Источник | Тип | Что делать |
| --- | --- | --- |
| Параметр без аннотации | `any` (ошибка под `noImplicitAny`) | аннотировать |
| `JSON.parse(text)` | `any` по объявлению в `lib.d.ts` | обернуть в функцию, возвращающую `unknown` |
| `response.json()` у `fetch` | `Promise<any>` | то же |
| `catch (error)` | `unknown` под `strict`, иначе `any` | включить `strict` |
| Библиотека без деклараций | `any` для всего модуля | найти `@types` или написать декларацию |
| Обращение по несуществующему пути через `any` | `any` | устранить исходный `any` |

**`unknown`** - тип, включающий все значения: в него присваивается что угодно,
но сам он присваивается только в `unknown` и `any`, а обращение к членам
запрещено, пока тип не сужен проверкой.

```ts
let value: unknown = 42;
value = 'text';
value = { name: 'Ann' };

// value.toUpperCase();
// Ошибка TS18046: 'value' is of type 'unknown'.

// const s: string = value;
// Ошибка TS2322: Type 'unknown' is not assignable to type 'string'.

if (typeof value === 'string') {
  console.log(value.toUpperCase()); // после проверки value: string
}
```

`unknown` - правильный тип для любого значения, пришедшего извне: тела
запроса, результата `JSON.parse`, переменной окружения, аргумента `catch`.
Компилятор заставляет проверить значение до использования, и проверка
превращается в сужение типа:

```ts
/**
 * Разбирает JSON, не притворяясь, что знает форму результата.
 *
 * Возвращает unknown вместо any: вызывающий код обязан проверить структуру
 * до обращения к полям.
 */
function parseJson(text: string): unknown {
  return JSON.parse(text);
}

const data = parseJson('{"name":"Ann"}');

if (
  typeof data === 'object' &&
  data !== null &&
  'name' in data && // после этой проверки data: object & { name: unknown }
  typeof data.name === 'string'
) {
  console.log(data.name.toUpperCase()); // data.name: string
}
```

Такие цепочки проверок выносятся в предикаты типов
([7.3](narrowing.md#73-пользовательские-предикаты-типов-value-is-t)) или
заменяются схемной валидацией на границе приложения
([7.6](narrowing.md#76-паттерны-тип-результата-состояние-асинхронной-операции-валидация-unknown-на-границе)).

Под `strict` переменная в `catch` тоже имеет тип `unknown`, потому что в
JavaScript бросить можно что угодно:

```ts
function readConfig(): void {
  try {
    JSON.parse('{');
  } catch (error) {
    // console.log(error.message);
    // Ошибка TS18046: 'error' is of type 'unknown'.
    if (error instanceof Error) {
      console.log(error.message);
    }
  }
}
```

### Сравнение

| | `any` | `unknown` |
| --- | --- | --- |
| Присвоить в него | что угодно | что угодно |
| Присвоить из него | куда угодно | только в `unknown` и `any` |
| Обращение к членам | без проверки | ошибка до сужения |
| `string \| T` | `any` | `unknown` |
| `string & T` | `any` | `string` |
| Место в модели множеств | вне модели: одновременно и верх, и низ | универсальное множество |

Две последние строки объясняют, почему `any` заразен, а `unknown` - нет.
`unknown` подчиняется алгебре множеств: объединение с универсальным множеством
дает универсальное, пересечение - исходное. `any` не подчиняется ничему: он
поглощает все и в объединении, и в пересечении.

### Где `any` уместен

Единственное регулярное применение `any` в типизированном коде - ограничение
«любая функция»:

```ts
type AnyFunction = (...args: any[]) => any;

const increment = (x: number): number => x + 1;
const asAny: AnyFunction = increment; // допустимо

// type UnknownFunction = (...args: unknown[]) => unknown;
// const asUnknown: UnknownFunction = increment;
// Ошибка TS2322: Type '(x: number) => number' is not assignable to type 'UnknownFunction'.
//   Types of parameters 'x' and 'args' are incompatible.
//     Type 'unknown' is not assignable to type 'number'.
```

`unknown[]` здесь не подходит: параметры функций проверяются в обратную
сторону - функция, принимающая `number`, не может стоять там, где обещали
принимать `unknown`
([5.6](functions.md#56-совместимость-функций-число-параметров-вариантность-strictfunctiontypes)).
`any` в этой позиции не отключает проверку у вызывающего кода: тип `T`,
ограниченный через `T extends AnyFunction`, сохраняет свою реальную сигнатуру
([10.5](mapped-and-conditional-types.md#105-infer-извлечение-типов-из-функций-промисов-массивов-и-кортежей)).

## 1.5 `void` и `never`

**`void`** - тип результата функции, значение которого не предназначено для
использования. В рантайме такая функция возвращает `undefined`.

**`never`** - тип, не содержащий ни одного значения: пустое множество. Функция
с типом `never` не возвращает управление - бросает исключение или не
завершается.

Разница не в том, что возвращается, а в том, продолжается ли выполнение после
вызова: после `void`-функции - да, после `never`-функции - нет.

### `void`

```ts
function log(message: string): void {
  console.log(message);
}

const result = log('hi'); // result: void, использовать его нечем
```

У `void` есть особенность, которая выглядит как противоречие. Функция,
*объявленная* с возвращаемым типом `void`, не может вернуть значение. Но
функциональный *тип* с результатом `void` принимает функцию, возвращающую что
угодно:

```ts
// function log(message: string): void {
//   return 42;
// Ошибка TS2322: Type 'number' is not assignable to type 'void'.

type Callback = () => void;
const callback: Callback = () => 42; // допустимо: результат будет проигнорирован
```

Причина - практическая. `forEach` объявляет callback как `(value) => void`, и
без этого правила нельзя было бы написать `list.forEach((x) => target.push(x))`:
`push` возвращает `number`. Тип `() => void` означает «результат не будет
использован», а не «результата нет». Подробнее о возвращаемых типах - в
[5.3](functions.md#53-возвращаемый-тип-вывод-и-явная-аннотация-void-в-callback-ах-promiset-у-async-функций).

### `never`

```ts
/**
 * Бросает исключение с сообщением.
 *
 * Аннотация never обязательна: без нее объявление функции получит тип void,
 * и компилятор не будет считать код после вызова недостижимым.
 */
function fail(message: string): never {
  throw new Error(message);
}

function loopForever(): never {
  while (true) {
    // Функция не завершается: тип never.
  }
}
```

Компилятор выводит `never` только для функциональных выражений. Объявление
функции с тем же телом получает `void`:

```ts
function failDeclared(message: string) {
  throw new Error(message); // выведено: void
}

const failArrow = (message: string) => {
  throw new Error(message); // выведено: never
};
```

Разница в выводе имеет практическое значение. Вызов функции с типом `never`
делает последующий код недостижимым, и компилятор использует это при сужении
типов:

```ts
/**
 * Возвращает строку, останавливая выполнение на null.
 *
 * После fail() ветка с null недостижима, и value сужается до string.
 */
function requireValue(value: string | null): string {
  if (value === null) {
    fail('value is null');
  }
  return value; // value: string
}
```

Если заменить `fail` на `failDeclared` с выведенным `void`, компилятор не
узнает, что ветка прерывается, и сообщит: `Type 'string | null' is not
assignable to type 'string'`. Поэтому функции, которые всегда бросают,
аннотируются `: never` явно.

### Проверка полноты

Главное применение `never` - **проверка полноты** (exhaustiveness checking):
после разбора всех вариантов объединения остаток сужается до `never`, и
присваивание его переменной типа `never` компилируется. Как только в
объединение добавляется вариант, не разобранный в `switch`, остаток перестает
быть пустым, и компилятор указывает на место, которое забыли обновить:

```ts
type Status = 'pending' | 'success' | 'error';

/**
 * Возвращает подпись статуса.
 *
 * Ветка default фиксирует полноту разбора: если в Status добавится вариант,
 * присваивание в never перестанет компилироваться.
 */
function label(status: Status): string {
  switch (status) {
    case 'pending':
      return 'В работе';
    case 'success':
      return 'Готово';
    case 'error':
      return 'Ошибка';
    default: {
      const exhaustive: never = status;
      return exhaustive;
    }
  }
}
```

После добавления `'cancelled'` в `Status`:

```
Ошибка TS2322: Type '"cancelled"' is not assignable to type 'never'.
```

Тот же прием без лишней переменной записывается как `status satisfies never`
([8.5](type-operators.md#85-satisfies-проверка-без-расширения-типа)); разбор
размеченных объединений - в
[7.5](narrowing.md#75-размеченные-объединения-и-проверка-полноты-через-never).

### `never` в составных типах

Как пустое множество, `never` исчезает в объединении и поглощает пересечение:

```ts
type A = string | never; // string: ∅ ∪ S = S
type B = string & never; // never: ∅ ∩ S = ∅
```

На этом свойстве построена фильтрация объединений в условных типах
([10.4](mapped-and-conditional-types.md#104-распределение-по-объединениям-и-его-отключение))
и удаление ключей в отображаемых типах: ветка, дающая `never`, просто
выпадает из результата.

| | `void` | `never` | `undefined` |
| --- | --- | --- | --- |
| Значения | `undefined` | нет | `undefined` |
| Функция | завершается, результат не используется | не завершается | завершается, результат - `undefined` |
| Код после вызова | достижим | недостижим | достижим |
| `T \| X` | `T \| void` | `T` | `T \| undefined` |
| Присвоить в него | `undefined` | ничего | `undefined` |

## 1.6 `null` и `undefined` при `strictNullChecks`

**`strictNullChecks`** - режим компилятора, в котором `null` и `undefined` не
входят ни в один другой тип: `string` означает только строки, а строка либо
`null` записывается как `string | null`.

Без этого режима `null` и `undefined` принадлежат каждому типу, и запись
`let name: string = null` компилируется. Именно отсюда берется самая частая
ошибка рантайма в JavaScript - `Cannot read properties of undefined`. Режим
входит в `strict` ([2.5](tsconfig.md#25-strict-и-его-составляющие)), и весь
конспект написан в предположении, что он включен.

```ts
/**
 * Возвращает длину строки или 0 для null.
 *
 * Без проверки обращение к length - ошибка: null не имеет свойств.
 */
function getLength(text: string | null): number {
  // return text.length;
  // Ошибка TS18047: 'text' is possibly 'null'.
  if (text === null) {
    return 0;
  }
  return text.length; // text: string
}
```

### Откуда берутся `null` и `undefined`

| Источник | Тип | Замечание |
| --- | --- | --- |
| Необязательное свойство `age?: number` | `number \| undefined` | |
| Необязательный параметр `(x?: number)` | `number \| undefined` | |
| `Map.get`, `Array.prototype.find` | `V \| undefined` | |
| `document.querySelector` | `Element \| null` | |
| Индекс массива `list[i]` | `T` | `undefined` **не добавляется** без `noUncheckedIndexedAccess` |
| Свойство индексной сигнатуры `dict[key]` | `T` | то же |

Пятая и шестая строки - осознанный компромисс компилятора в пользу удобства:
доступ по индексу считается всегда успешным. Опция `noUncheckedIndexedAccess`
([2.6](tsconfig.md#26-дополнительные-проверки-nouncheckedindexedaccess-exactoptionalpropertytypes-noimplicitoverride-и-другие))
добавляет `undefined` и к этим случаям.

```ts
interface Person {
  name: string;
  age?: number;
}

const cache = new Map<string, number>();
const hit = cache.get('a'); // number | undefined

const root = document.querySelector('#app'); // Element | null

const scores = [10, 20];
const third = scores[2]; // number по типу, undefined в рантайме

// function birthYear(person: Person): number {
//   return 2026 - person.age;
// Ошибка TS18048: 'person.age' is possibly 'undefined'.
```

### Способы обработки

| Способ | Пример | Замечание |
| --- | --- | --- |
| Явное сравнение | `if (x === null)` | сужает тип в ветке |
| Проверка истинности | `if (x)` | отсекает также `0`, `''`, `false` и `NaN` |
| Ранний выход | `if (!x) { return; }` | сужает тип до конца функции |
| Optional chaining | `config.host?.length` | результат снова включает `undefined` |
| Nullish coalescing | `config.port ?? 3000` | замена только `null` и `undefined` |
| Логическое ИЛИ | `config.port \|\| 3000` | замена всех ложных значений, включая `0` |
| Ненулевое утверждение | `x!` | отключает проверку, [8.6](type-operators.md#86-утверждения-типов-as--двойное-утверждение-через-unknown-границы-допустимого) |

```ts
interface Config {
  port?: number;
  host?: string;
}

function resolvePort(config: Config): number {
  return config.port ?? 3000; // port: 0 сохраняется
}

function hostLength(config: Config): number {
  return config.host?.length ?? 0; // host?.length: number | undefined
}
```

Разница между `??` и `||` проверяется прогоном:

```ts
const config: { port?: number; name?: string } = { port: 0, name: '' };
console.log(config.port ?? 3000, config.name ?? 'anonymous'); // 0 ''
console.log(config.port || 3000, config.name || 'anonymous'); // 3000 'anonymous'
```

`||` подменяет допустимые значения `0` и `''`, и это ошибка, которую тип не
ловит: оба выражения имеют тип `number` и `string`. Механика сужения в
условиях, включая ловушку истинности, - в
[7.1](narrowing.md#71-анализ-потока-управления-проверки-присваивания-истинность-равенство).

## 1.7 Стирание типов: что остается в JavaScript

**Стирание типов** (type erasure) - свойство компиляции, при котором все
конструкции системы типов удаляются из результата: аннотации, интерфейсы,
псевдонимы, параметры обобщений, утверждения типов.

Исходный файл:

```ts
interface User {
  id: number;
  name: string;
}

type UserId = User['id'];

function describe<T extends User>(user: T): string {
  const id: UserId = user.id;
  return `${id}: ${user.name}`;
}

const admin: User = { id: 1, name: 'Ann' };

console.log(describe(admin));
```

Результат `tsc --target es2022`:

```js
"use strict";
function describe(user) {
    const id = user.id;
    return `${id}: ${user.name}`;
}
const admin = { id: 1, name: 'Ann' };
console.log(describe(admin));
```

Интерфейс, псевдоним, параметр `T`, ограничение `extends` и все аннотации
исчезли. В рантайме нет ни `User`, ни способа узнать, что `admin` ему
соответствовал.

### Следствия

1. **Проверка типа в рантайме невозможна.** Интерфейс нельзя использовать в
   `instanceof`, а `typeof` знает только восемь тегов JavaScript.

   ```ts
   // function isPoint(value: unknown): boolean {
   //   return value instanceof Point;
   // Ошибка TS2693: 'Point' only refers to a type, but is being used as a value here.
   ```

2. **Данные извне не типизированы.** Ответ сервера, тело запроса, содержимое
   файла, переменные окружения - для компилятора это `unknown` или, хуже,
   `any`. Утверждение `JSON.parse(text) as User` ничего не проверяет: оно
   стирается вместе с остальными типами
   ([8.6](type-operators.md#86-утверждения-типов-as--двойное-утверждение-через-unknown-границы-допустимого)).
   Проверка структуры - это код, который нужно написать
   ([15.6](node-express.md#156-валидация-на-границе-тело-запроса-как-unknown-схемы-и-вывод-типа-из-схемы)).

3. **Параметр обобщения - не значение.** `new T()` внутри обобщенной функции
   невозможен; чтобы создать экземпляр, нужно передать конструктор как
   обычный аргумент
   ([6.6](classes.md#66-тип-экземпляра-и-тип-конструктора-ограничение-на-конструктор-миксины)).

4. **Типы ничего не стоят в рантайме.** Сколь угодно сложный тип не влияет ни
   на размер бандла, ни на скорость программы. Влияет он только на время
   проверки ([18.5](build-and-performance.md#185-стоимость-типов-взрыв-объединений-глубина-рекурсии-пределы-компилятора)).

### Что не стирается

Часть синтаксиса TypeScript порождает JavaScript-код, а не только типы:

| Конструкция | Что генерируется | Раздел |
| --- | --- | --- |
| `enum` | объект с прямым и обратным отображением | [3.3](arrays-tuples-enums.md#33-перечисления-числовые-строковые-const-enum-представление-в-javascript) |
| `const enum` | инлайн значений в местах использования | [3.3](arrays-tuples-enums.md#33-перечисления-числовые-строковые-const-enum-представление-в-javascript) |
| `namespace` со значениями | функция-обертка и объект | [13.4](modules.md#134-пространства-имен-против-модулей) |
| Параметры-свойства `constructor(public x: number)` | присваивания в конструкторе | [6.1](classes.md#61-поля-и-конструктор-инициализация-strictpropertyinitialization-параметры-свойства) |
| Декораторы | вызовы вспомогательных функций | [12.1](decorators.md#121-две-реализации-experimentaldecorators-и-стандартные-декораторы-typescript-5) |
| `import x = require(...)` | `require` | [13.1](modules.md#131-es-модули-и-commonjs-синтаксис-семантика-вывод-компилятора) |

Например, `enum Level { Low, High }` превращается в:

```js
var Level;
(function (Level) {
    Level[Level["Low"] = 0] = "Low";
    Level[Level["High"] = 1] = "High";
})(Level || (Level = {}));
```

Различие стало практически важным с появлением запуска TypeScript без
компилятора. Node.js начиная с версии 23 выполняет `.ts`-файлы напрямую,
**только стирая** типы (режим strip-only): он не анализирует программу и
поэтому не умеет генерировать код для конструкций из таблицы.

```
$ node user.ts
1: Ann

$ node enum.ts
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode
```

Опция компилятора `erasableSyntaxOnly` (TypeScript 5.8) запрещает
нестираемый синтаксис заранее, ошибкой TS1294 на этапе проверки.

Та же граница проходит через импорты. Компилятор знает, что `Shape` -
интерфейс, и сам удаляет его из `import { Shape, unit }`. Инструмент, который
только стирает типы, этого не знает, оставляет импорт как есть, и в рантайме
модуль сообщает: `The requested module './shapes.ts' does not provide an
export named 'Shape'`. Решение - пометить импорт типа явно:

```ts
import { type Shape, unit } from './shapes.ts';
```

Опция `verbatimModuleSyntax` требует такой пометки для каждого импорта типа
(ошибка TS1484) и тем самым делает вывод компилятора и инструмента-стирателя
одинаковым ([13.3](modules.md#133-импорт-и-экспорт-только-типов-import-type-verbatimmodulesyntax)).

## Типичные ошибки

1. **Типы-обертки в аннотациях.** `String`, `Number`, `Boolean`, `Object` -
   объектные типы оберток. Примитив в них присваивается, обратно - нет, и
   рано или поздно `new String('a')` встретится с параметром `string`.
2. **Номинативное мышление.** Ожидание, что `type UserId = string` и
   `type OrderId = string` несовместимы. Псевдоним не создает нового типа;
   различить их можно только меткой
   ([4.4](object-types.md#44-пересечения-слияние-свойств-конфликт-свойств-и-never-branded-types)).
3. **Расширенный литерал против объединения литералов.** Свойство
   `{ role: 'admin' }` имеет тип `string`, и передать его в параметр
   `'admin' | 'user'` нельзя. Исправляется аннотацией или `as const`, а не
   утверждением `as 'admin'`.
4. **`any` из `JSON.parse` и `catch`.** Один необъявленный `any` на входе
   превращает в `any` всю цепочку вычислений. Входные данные объявляются как
   `unknown` и проверяются.
5. **`void` прочитан как «возвращает `undefined`».** Callback типа
   `() => void` может вернуть что угодно, и полагаться на его результат
   нельзя; при этом объявленная `void`-функция вернуть значение не может.
6. **Функция-объявление с `throw` без аннотации.** Ее тип - `void`, а не
   `never`, и сужение после вызова не происходит. Функции, которые всегда
   бросают, аннотируются `: never`.
7. **`!` и `as` вместо обработки `null`.** Утверждение убирает ошибку
   компиляции, но не `undefined` из данных. Тип обещает то, чего в рантайме
   нет.
8. **Ожидание проверок от стертых типов.** `value instanceof Interface` не
   компилируется, `data as User` не проверяет `data`, а `enum` и параметры
   свойств не работают в инструментах, которые только стирают типы.
