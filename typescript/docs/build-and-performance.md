# 18 Сборка и производительность

[← К содержанию](../README.md)

Компилятор делает две независимые вещи: **проверяет** типы и **генерирует**
JavaScript. Вторая быстра и не требует первой; первая - вся стоимость
TypeScript, и она растет с размером проекта и сложностью типов. Тема о том,
как разделить эти две работы между инструментами, как не проверять заново
то, что не менялось, и на что уходит время проверки. Все числа в теме -
замеры на этой машине: синтетический проект из 2000 модулей (90 тысяч
строк), TypeScript 5.9.3 и 7.0.2, esbuild 0.28; каждое время - медиана
трех запусков. Абсолютные значения на другой машине будут другими,
соотношения - нет.

---

## 18.1 Проверка и эмит: `tsc`, `noEmit`, транспиляция без проверки (esbuild, swc, Babel)

`tsc` без опций проверяет программу целиком и записывает результат. Два
флага разделяют работы: `noEmit` - только проверка, `noCheck` (5.5) -
только генерация. Однофайловые транспиляторы - esbuild, swc, Babel, режим
stripping в Node - делают только второе и ничего не знают о типах.

| Режим | 5.9 | 7.0 |
| --- | --- | --- |
| `tsc` - проверка и генерация | 2.05 с | 0.50 с |
| `tsc --noEmit` - только проверка | 1.61 с | 0.36 с |
| `tsc --noCheck` - только генерация | | 0.30 с |
| `esbuild` - только генерация | 0.36 с | |

Два вывода из таблицы. Генерация стоит дешево и одинаково у всех
инструментов: `tsc --noCheck` и esbuild отличаются на сотые доли секунды.
Все, что дороже, - проверка, и именно ее нужно организовывать.

Второй вывод - разрыв между версиями. Компилятор 7.0 - нативная реализация
на Go с параллельной проверкой ([2](tsconfig.md#2-настройка-компилятора)):
на этом проекте проверка быстрее в 4,5 раза, а с `--singleThreaded` - в
2,4 (0,66 с). По данным анонса 7.0, на больших кодовых базах разница
достигает 8-12 раз (VS Code: 125,7 с → 10,6 с). Флаги `--checkers` и
`--builders` управляют числом параллельных проверяющих и сборщиков.

### Разделение работ

Стандартная схема современного проекта - генерацию делает сборщик или
транспилятор, проверку - `tsc --noEmit` отдельным шагом:

| Где | Инструмент | Задача |
| --- | --- | --- |
| Разработка | Vite/esbuild, swc, `node file.ts` | мгновенная генерация без проверки |
| Редактор | языковой сервер TypeScript | проверка открытых файлов, подсказки |
| Перед коммитом и в CI | `tsc --noEmit` | полная проверка |
| Сборка библиотеки | `tsc` или `tsc --emitDeclarationOnly` + esbuild | код и декларации |

Схема работает при условии, что однофайловый транспилятор дает тот же
результат, что `tsc`. Это обеспечивают `isolatedModules` и
`verbatimModuleSyntax` ([2.4](tsconfig.md#24-совместимость-модулей-esmoduleinterop-allowsyntheticdefaultimports-isolatedmodules-verbatimmodulesyntax)),
а для stripping в Node - еще и `erasableSyntaxOnly`
([1.7](type-system.md#17-стирание-типов-что-остается-в-javascript)).
Без них код, который прошел `tsc`, может сломаться в транспиляторе - или
наоборот.

Цена схемы - проверка типов не блокирует запуск: код с ошибками типов
запускается. Для разработки это удобно, для CI обязателен отдельный шаг
`tsc --noEmit`, иначе ошибки не поймает никто.

## 18.2 Инкрементальная компиляция: `incremental`, `tsBuildInfoFile`, режим `watch`

`incremental: true` сохраняет после компиляции файл `.tsbuildinfo` с
сигнатурами всех файлов программы (хеши деклараций) и графом зависимостей.
При следующем запуске компилятор проверяет заново только файлы, которые
изменились, и те, что зависят от изменившихся **сигнатур**.

```json
{
  "compilerOptions": {
    "incremental": true,
    "tsBuildInfoFile": "dist/.tsbuildinfo"
  }
}
```

| Запуск | 5.9 | 7.0 |
| --- | --- | --- |
| Первый, без `.tsbuildinfo` | 2.10 с | 0.71 с |
| Без изменений | 0.57 с | 0.18 с |
| Комментарий в модуле-листе | 0.63 с | 0.21 с |
| Комментарий в модуле с 22 зависимыми | 0.62 с | 0.21 с |
| Новое поле в экспортированном интерфейсе с 22 зависимыми | ≈1.6 с | ≈0.37 с |

Комментарий не меняет сигнатуру файла - его декларация та же, - поэтому
зависимые модули не перепроверяются, сколько бы их ни было. Изменение
экспортированного типа меняет сигнатуру, и все, кто его импортирует
(транзитивно), проверяются заново; в этом проекте это почти вся программа.
Отсюда практическое правило: чем меньше модулей импортируют часто
меняющийся тип, тем дешевле пересборки.

`tsBuildInfoFile` задает расположение файла; по умолчанию он ложится рядом
с `outDir` или `tsconfig.json`. Файл не коммитится, но сохраняется между
запусками в CI, если кэш это позволяет. `incremental` работает и с
`noEmit` - для проверки без генерации.

### `watch`

`tsc --watch` держит программу в памяти и перепроверяет измененные файлы
при сохранении, используя тот же механизм сигнатур. В 7.0 наблюдение за
файлами переписано на нативный watcher, и режим стал заметно
устойчивее на больших деревьях. Для разработки `watch` в терминале обычно
дублирует языковой сервер редактора; его место - непрерывная проверка на
сервере сборки и в редакторах без поддержки TypeScript.

## 18.3 Project references: `composite`, `references`, `tsc -b`, монорепозитории

**Project references** - способ разбить кодовую базу на несколько проектов
с собственными `tsconfig.json`, где один проект ссылается на другой, а
компилятор собирает их в правильном порядке и не пересобирает
неизменившиеся.

Пример - монорепозиторий с общей библиотекой и сервером, использующим ее:

```json
{
  "compilerOptions": {
    "composite": true,
    "module": "nodenext",
    "target": "es2024",
    "lib": ["es2024"],
    "types": [],
    "rootDir": "src",
    "outDir": "dist",
    "strict": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```

```json
{
  "compilerOptions": {
    "module": "nodenext",
    "target": "es2024",
    "lib": ["es2024"],
    "types": ["node"],
    "rootDir": "src",
    "outDir": "dist",
    "strict": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true
  },
  "references": [{ "path": "../shared" }],
  "include": ["src"]
}
```

```json
{ "files": [], "references": [{ "path": "packages/shared" }, { "path": "packages/server" }] }
```

Первый файл - `packages/shared/tsconfig.json`, второй -
`packages/server/tsconfig.json`, третий - корневой, который сам ничего не
компилирует и только перечисляет проекты. Сервер импортирует
`@app/shared` как обычный пакет: в монорепозитории с workspaces
`node_modules/@app/shared` - ссылка на `packages/shared`, а `exports` его
`package.json` указывает на `dist` ([14.6](declarations.md#146-публикация-типизированной-библиотеки-types-и-exports-в-packagejson)).

| Требование | Зачем |
| --- | --- |
| `composite: true` у проекта, на который ссылаются | компилятор обязан знать все его файлы и генерировать декларации; `declaration` и `incremental` включаются автоматически |
| Все исходники перечислены в `include` или `files` | ссылающийся проект должен уметь найти декларацию для любого импорта |
| `references` у ссылающегося проекта | компилятор берет типы из `dist/*.d.ts` зависимости, а не из ее исходников |

Сборка - командой `tsc -b` (build mode): она обходит граф `references`,
собирает проекты в порядке зависимостей и пропускает те, чьи входы не
менялись:

```
$ tsc -b --verbose
Projects in this build:
    * packages/shared/tsconfig.json
    * packages/server/tsconfig.json
    * tsconfig.json
Project 'packages/shared/tsconfig.json' is out of date because output file 'packages/shared/tsconfig.tsbuildinfo' does not exist
Building project 'packages/shared/tsconfig.json'...
Project 'packages/server/tsconfig.json' is out of date because output file 'packages/server/tsconfig.tsbuildinfo' does not exist
Building project 'packages/server/tsconfig.json'...

$ tsc -b --verbose
Project 'packages/shared/tsconfig.json' is up to date because newest input 'packages/shared/src/index.ts' is older than output
Project 'packages/server/tsconfig.json' is up to date because newest input 'packages/server/src/main.ts' is older than output
```

Обычный `tsc -p packages/server` граф не обходит: если `shared` еще не
собран, его `dist` пуст, и импорт не разрешается - TS2307
`Cannot find module '@app/shared'`. В 7.0 `tsc -b` собирает независимые
проекты параллельно (`--builders`).

### Когда нужны

Project references окупаются, когда кодовая база слишком велика для одной
программы или когда части имеют разные настройки: библиотека с
`declaration` и сервер без, код для браузера с `dom` и код для Node без.
Для проекта из одного пакета они только усложняют конфигурацию;
`incremental` дает ту же экономию на пересборках.

## 18.4 Ускорение проверки типов: `skipLibCheck`, границы `include`, явные типы экспортов, `interface` против пересечений

Когда проверка стала медленной, первое действие - измерить. `tsc
--extendedDiagnostics` печатает число файлов, типов, инстанцирований и
время по фазам; `tsc --generateTrace каталог` записывает трассу для
анализа в `@typescript/analyze-trace` или в профилировщике Chrome и
показывает, какие файлы и типы стоят дороже всего.

```
Files:            2070
Types:          105333
Instantiations: 220631
Memory used:   289458K
Check time:      0.159s
Total time:      0.251s
```

### `skipLibCheck`

Декларации библиотек - часто самая большая часть программы. Файл из шести
строк, импортирующий типы Express, React и Redux Toolkit, тянет за собой
194 файла деклараций:

| | 5.9 | 7.0 |
| --- | --- | --- |
| `skipLibCheck: false` | 1.23 с | 0.32 с |
| `skipLibCheck: true` | 0.40 с | 0.11 с |

Трехкратная разница - на проверке файлов, которые проект не может изменить.
Цена опции разобрана в [2.6](tsconfig.md#26-дополнительные-проверки-nouncheckedindexedaccess-exactoptionalpropertytypes-noimplicitoverride-и-другие):
ошибки в собственных `.d.ts` тоже не проверяются.

### Границы программы

Все, что попало в программу, проверяется ([2.1](tsconfig.md#21-структура-tsconfigjson-compileroptions-include-exclude-extends)).
Типичные лишние файлы: тесты в конфигурации сборки, сгенерированный код,
`dist` предыдущей сборки, второй набор глобальных деклараций (`@types/jest`
и `@types/mocha` разом). Опция `types` с явным списком вместо
автоподключения всех `@types` - часть той же гигиены, и с 6.0 это
умолчание.

### Явные типы экспортов

Компилятор выводит тип каждого экспорта, у которого нет аннотации, а
при `declaration` еще и записывает выведенный тип - часто длиннее
любого имени. Руководство по производительности TypeScript рекомендует
аннотировать возвращаемые типы экспортируемых функций: именованный тип
компактнее выведенного анонимного, и это экономит время и на проверке, и
на генерации деклараций. Второй эффект - ошибка в теле функции
локализуется в ней, а не расходится по всем местам вызова. Опция
`isolatedDeclarations` ([14.1](declarations.md#141-файлы-dts-declare-ambient-декларации-генерация-через-declaration))
делает аннотации обязательными.

### `interface` против пересечений

Та же рекомендация из руководства - расширять объектные типы через
`interface extends`, а не через `&` ([4.5](object-types.md#45-type-против-interface-расширение-слияние-деклараций-выбор)).
Замер на 120 типах по 24 части каждый и 1200 проверках совместимости
между ними:

| | 5.9 | 7.0 |
| --- | --- | --- |
| `interface Big extends Part0, Part1, ...` | 0.30 с | 0.19 с |
| `type Big = Part0 & Part1 & ...` | 0.49 с | 0.29 с |

Полтора раза - на одинаковом коде. Интерфейс сравнивается как один плоский
тип, и результат сравнения кэшируется; пересечение при каждой проверке
обходится по составляющим. На простых формах с одним-двумя членами разница
не измерима - она появляется на глубоких композициях, которые проверяются
много раз.

## 18.5 Стоимость типов: взрыв объединений, глубина рекурсии, пределы компилятора

Типы ничего не стоят в рантайме ([1.7](type-system.md#17-стирание-типов-что-остается-в-javascript)),
но стоят при каждой проверке. Три источника дорогих типов - и у каждого
есть жесткий предел, за которым компилятор отказывается работать.

### Взрыв объединений

Шаблонный литерал с объединениями в подстановках - декартово произведение
([11.1](template-literal-types.md#111-синтаксис-и-комбинирование-объединений)).
Тип `` `${Ten}${Ten}${Ten}${Ten}` `` - 10 000 членов, и каждое
использование такого типа - сравнение с каждым членом. Файл с 200
функциями, принимающими этот тип, против того же файла с образцом
`` `${Ten}${string}` ``:

| | Типов | 5.9 | 7.0 |
| --- | --- | --- | --- |
| Объединение из 10⁴ литералов | 11 422 | 0.08 с | 0.027 с |
| Образец `` `${Ten}${string}` `` | 324 | 0.02 с | 0.002 с |

Предел - около ста тысяч членов: 10⁵ дает TS2590 `Expression produces a
union type that is too complex to represent`. Точное перечисление нужно
редко; образец с `${string}` проверяет форму строки без перечисления.
Тот же эффект дают большие размеченные объединения, прогоняемые через
распределительные условные типы: каждый член - отдельное инстанцирование.

### Глубина рекурсии

Рекурсивный условный тип раскрывается при каждом использовании до
базового случая. Предел - около 50 уровней для обычной рекурсии и 1000 для
хвостовой ([10.6](mapped-and-conditional-types.md#106-рекурсивные-типы-и-предел-глубины)),
ошибка - TS2589 `Type instantiation is excessively deep and possibly
infinite`. До предела рекурсия стоит пропорционально глубине на каждое
**новое** инстанцирование.

Слово «новое» важно: результаты инстанцирования кэшируются по аргументам.
Тип `Paths<Config>`, использованный в трехстах функциях, вычисляется один
раз - замер показал одинаковое число инстанцирований для варианта с
именованным промежуточным типом и без него. Именование промежуточных
типов улучшает сообщения об ошибках и декларации, но не скорость; дорого
не повторное использование, а **разные** аргументы: `Paths<T>` для сотни
разных `T` - сто раскрытий.

### Пределы

| Предел | Ошибка | Обход |
| --- | --- | --- |
| Объединение ≥ 10⁵ членов | TS2590 | образец вместо перечисления |
| Рекурсия ≈ 50 уровней (1000 хвостовая) | TS2589 | аккумулятор, хвостовая форма |
| Сложность сравнения типов | TS2589 или TS2321 `Excessive stack depth comparing types` | упростить обобщение, добавить явную аннотацию |

### Практика

1. Измерять: `--extendedDiagnostics` до и после изменения; `--generateTrace`
   для поиска виновника.
2. Тяжелые типы - на границах: в описании API, схемы, маршрутов, а не в
   типах пропсов и параметрах функций, которые проверяются в тысяче мест.
3. Обобщенные функции с условными типами результата дороже перегрузок с
   конкретными типами ([5.4](functions.md#54-перегрузки-сигнатуры-и-реализация-когда-объединение-или-обобщение-лучше))
   там, где вариантов немного.
4. Аннотация возвращаемого типа у экспортов останавливает вывод и
   распространение сложных типов по проекту.

## Типичные ошибки

1. **Сборка без отдельной проверки.** Транспилятор не проверяет типы;
   без `tsc --noEmit` в CI ошибки типов доходят до продакшена.
2. **Расчет на транспилятор без `isolatedModules`/`verbatimModuleSyntax`.**
   Код, прошедший `tsc`, может сломаться у однофайлового инструмента -
   реэкспорт типов, `const enum`.
3. **Часто меняющийся тип в модуле, который импортируют все.** Каждое
   изменение сигнатуры перепроверяет всех зависимых; такие типы выносятся в
   узкие модули.
4. **`tsc -p` вместо `tsc -b` при project references.** Зависимый проект
   не собирается, и импорт не разрешается (TS2307).
5. **`composite` без всех файлов в `include`.** Ссылающийся проект не
   находит декларацию для импорта.
6. **Тесты и `dist` в программе сборки.** Лишние файлы проверяются
   наравне с исходниками; для тестов - отдельная конфигурация.
7. **Перечисление всех комбинаций там, где хватило бы образца.**
   Произведение объединений растет до предела TS2590 и замедляет каждую
   проверку.
8. **Ожидание, что именование промежуточного типа ускорит проверку.**
   Инстанцирования кэшируются по аргументам; имя помогает читаемости, а не
   скорости.
