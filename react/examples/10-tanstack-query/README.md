# 10 · TanStack Query

Та же «Лавка», но серверные данные вынесены в отдельный слой. Каталог
запрашивается `useQuery` и живет в кеше; проверка промокода и оформление
заказа - мутации. В сторе остается только то, чем владеет само приложение:
позиции корзины, способ доставки и открытое окно заказа.

## Что здесь показано

| Прием | Где |
| --- | --- |
| Разделение состояния: серверное - в кеше запросов, клиентское - в сторе | `api/queries.ts`, `store/cart-store.ts` |
| `queryOptions`: ключ и функция запроса вместе, с выводом типов | `api/queries.ts` |
| Ключи в одном месте, чтобы инвалидация не зависела от места вызова | `api/queries.ts` |
| `staleTime`: пока данные свежие, повторные запросы не уходят | `api/queries.ts` |
| `signal` от библиотеки вместо своего `AbortController` | `api/queries.ts` |
| Запрос прямо в компоненте: без эффекта, действия загрузки и статусов в сторе | `components/catalog.tsx` |
| `useMutation` с `onSuccess`: результат уходит в клиентское состояние | `hooks/use-promo-mutation.ts` |
| Инвалидация каталога после заказа: остатки изменились | `hooks/use-order-mutation.ts` |
| `setQueryData`: созданный заказ кладется в кеш без отдельного запроса | `hooks/use-order-mutation.ts` |
| `mutate` с колбэками вместо `mutateAsync`: необработанного отклонения не будет | `components/promo-form.tsx` |
| `QueryClientProvider` и панель `ReactQueryDevtools` | `app.tsx` |
| Клиент с настройками по умолчанию; в тестах повторы отключены | `api/query-client.ts` |

## Чем отличается от предыдущих вариантов

| Варианты 04-09 | Вариант 10 |
| --- | --- |
| каталог загружается действием и лежит в сторе | каталог - запрос, данные лежат в кеше |
| статусы `loading`/`error` пишутся руками в каждом срезе | `status`, `isFetching`, `error` приходят из `useQuery` |
| отмена запроса - свой `AbortController` или средства библиотеки состояния | `signal` передает сама библиотека |
| повторы после ошибки - вручную, обычно их просто нет | `retry` из коробки |
| «данные устарели» приходится придумывать | `staleTime` и инвалидация по ключу |
| после заказа приходится самому решать, что перезапросить | `invalidateQueries({ queryKey })` |

Клиентское состояние живет в Zustand - это обычная связка: библиотека
серверного состояния не пытается хранить корзину, а стор не пытается
кешировать ответы сервера. Дублировать каталог в сторе нельзя: две копии
одних и тех же данных неизбежно разойдутся.

Ловушка, которую поймал собственный тест: клиент по умолчанию повторяет
неудачный запрос дважды, и проверка ошибки в интерфейсе висела до таймаута,
потому что второй ответ mock-API оказывался успешным. Поэтому фабрика
клиента принимает параметр повторов, а тесты создают клиент с `retry: false` -
как и советует документация.
