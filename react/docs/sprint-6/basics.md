# Подходы, виды тестов и инструменты

## 6.1 Подходы: TDD, TLD, BDD

> 📌 **Автоматический тест** - программа, которая выполняет тестируемый код
> с заданными входными данными и сравнивает результат с ожидаемым; при
> расхождении тест «падает», а сообщение указывает, что именно разошлось.

Подходы различаются тем, **когда** пишется тест относительно кода.

> 📌 **TDD (Test-Driven Development)** - разработка через тестирование:
> тест пишется до кода, сначала падает, затем пишется минимальный код,
> который его проходит, после чего код улучшается без изменения поведения.

```
   красный ──► зеленый ──► рефакторинг ──► красный ──► …
   тест       минимальный  улучшение без     следующий
   падает     код проходит смены поведения   тест
```

TDD заставляет сформулировать ожидаемое поведение **до** реализации:
разработчик описывает контракт компонента - какие props, какой результат, -
не зная еще, как компонент устроен внутри. Побочный эффект - код получается
тестируемым по построению: то, что трудно протестировать, не пишется.

> 📌 **TLD (Test-Last Development)** - тесты пишутся после кода, по готовой
> реализации.

Самый распространенный на практике подход. Риск - тест повторяет
реализацию вместо того, чтобы проверять поведение: если написать его,
глядя на код, он подтвердит, что код делает то, что делает, а не то, что
должен.

> 📌 **BDD (Behavior-Driven Development)** - вариант TDD, в котором тесты
> формулируются как сценарии поведения на языке предметной области:
> «дано - когда - тогда» (Given - When - Then), и служат одновременно
> спецификацией.

В коде BDD виден в именовании: `describe('корзина')`, `it('пересчитывает
итог после удаления товара')` - предложения о поведении, а не о функциях.
Библиотеки вроде Cucumber идут дальше и позволяют писать сценарии текстом
(Gherkin), привязывая шаги к коду.

Термины «черный ящик» и «белый ящик» относятся не к подходу, а к тому, что
тест знает о реализации: тест черного ящика проверяет только вход и выход,
белого - опирается на внутреннее устройство. ✅ Тесты React-компонентов
пишутся как тесты черного ящика: через то, что видит пользователь.

## 6.2 Виды тестов

| Вид | Что проверяет | Изоляция | Скорость | Что ловит |
| --- | --- | --- | --- | --- |
| **Модульный (unit)** | Одну функцию, хук или компонент | Зависимости заменены заглушками | Миллисекунды | Ошибки логики в одном месте |
| **Интеграционный** | Несколько модулей вместе: компонент + хранилище + маршрутизатор, с заглушкой сети | Реальные модули, поддельная сеть | Десятки миллисекунд | Ошибки на стыках: неверный селектор, неправильное действие |
| **Сквозной (end-to-end, E2E)** | Приложение целиком в браузере, как пользователь | Ничего не заменено (или только бэкенд) | Секунды | Ошибки сборки, маршрутизации, реального API |

> 📌 **Модульный тест** - проверка одного модуля в изоляции от остальных:
> функции, хука или компонента с заглушками вместо внешних зависимостей.

> 📌 **Интеграционный тест** - проверка совместной работы нескольких
> модулей приложения без запуска его целиком; в React - компонент вместе с
> его реальными хуками, хранилищем и маршрутизатором при поддельной сети.

> 📌 **Сквозной тест (E2E)** - проверка сценария пользователя в настоящем
> браузере на собранном приложении: переходы, ввод, запросы к серверу.

### Сколько каких

Классическая **пирамида тестирования** - много модульных, меньше
интеграционных, единицы сквозных - исходит из стоимости: чем выше по
пирамиде, тем тест медленнее и хрупче. Для интерфейсов ее уточняют: центр
тяжести - **интеграционные тесты** компонентов, потому что модульный тест
компонента в полной изоляции (с заглушками вместо дочерних компонентов и
хуков) почти ничего не гарантирует, а сквозные слишком дороги, чтобы
покрыть ими каждую ветку.

```
                 ▲
             E2E │ ▲          несколько сценариев: вход, покупка, ключевые пути
                 │ │
     интеграция  │ █████      основная масса: компонент + хранилище + маршрутизатор
                 │ │
      модульные  │ ███        чистая логика: редьюсеры, селекторы, утилиты, хуки
                 │ │
   статические   │ ████████   TypeScript и ESLint: бесплатный нижний слой
                 └──────────────────────────────────────────────────────►
```

Нижний слой - **статический анализ**: TypeScript ловит целый класс ошибок
(неверный prop, `undefined` без проверки) без единого теста
([спринт 4](../sprint-4/README.md)).

### Что тестировать в React

Правило Testing Library: **чем больше тест похож на использование
приложения, тем больше уверенности он дает**. Отсюда:

| Тестировать | Не тестировать |
| --- | --- |
| Что видит пользователь: текст, роли, состояние кнопок | Внутреннее состояние компонента, вызовы `setState` |
| Что происходит по действию: клик, ввод, отправка формы | Имена CSS-классов, порядок вызова хуков |
| Что ушло наружу: вызов callback-prop, действие в хранилище, запрос | Что компонент отрендерил дочерний компонент с такими-то props |
| Чистую логику напрямую: редьюсеры, селекторы, утилиты | Реализацию сторонних библиотек |

Тест, привязанный к реализации, ломается при рефакторинге, не выявляя
ошибки, - и это худшее свойство теста.

## 6.3 Инструменты

Тест - это несколько инструментов, работающих вместе:

| Роль | Что делает | Сегодня | 🕰️ Ранее |
| --- | --- | --- | --- |
| **Раннер** | Находит файлы тестов, запускает их, показывает результат, следит за изменениями | **Vitest** (общая конфигурация с Vite, ESM, скорость) | Jest (по-прежнему жив, но требует отдельной настройки транспиляции); Mocha + Chai |
| **Среда выполнения** | DOM без браузера для рендера компонентов | **jsdom** или **happy-dom**; browser mode Vitest - настоящий браузер через Playwright | jsdom в Jest |
| **Утверждения (assertions)** | `expect(x).toBe(y)`; при расхождении - исключение с описанием | `expect` из Vitest (совместим с Jest) + **`jest-dom`** для DOM: `toBeInTheDocument`, `toBeDisabled`, `toHaveTextContent` | Chai `should`/`assert` |
| **Рендер и запросы** | Отрисовать компонент, найти элементы, выполнить действия | **Testing Library**: `render`, `screen`, запросы по роли; **`user-event`** для действий | Enzyme (`shallow`, `mount`) - без официального адаптера для React 17+ и без адаптеров для 18+; `react-test-renderer` - объявлен устаревшим в React 19 |
| **Заглушки (mocks)** | Заменить функцию, модуль, время, сеть | `vi.fn`, `vi.spyOn`, `vi.mock`, `vi.useFakeTimers`; сеть - **MSW** | `fetch-mock`, `redux-mock-store`, `jest.fn` |
| **Снапшоты** | Сохранить результат и сравнивать с ним | `toMatchSnapshot`, `toMatchInlineSnapshot` ([6.7](components.md#67-снапшоты)) | То же через `react-test-renderer` |
| **Покрытие** | Какие строки выполнились в тестах | `@vitest/coverage-v8` | Istanbul |
| **E2E** | Настоящий браузер | **Playwright**, **Cypress** ([6.10](redux-and-e2e.md#610-cypress)) | Selenium, Puppeteer |

> 📌 **Заглушка (mock)** - замена реальной зависимости управляемой
> подделкой: функция, которая записывает вызовы и возвращает заданное
> (`vi.fn`), подмена метода объекта (`vi.spyOn`), модуля (`vi.mock`),
> времени (`vi.useFakeTimers`) или сети (MSW).

### Расположение файлов

```
   src/
     components/
       cart/
         cart.tsx
         cart.test.tsx          рядом с компонентом: виден при открытии папки
         cart.module.css
     services/
       cart-slice.ts
       cart-slice.test.ts
   cypress/
     e2e/
       cart.cy.ts               сквозные тесты - отдельно: другой раннер, другая среда
     fixtures/
       items.json
   tests/
     setup.ts                   подключение jest-dom, MSW-сервер
```

`*.test.tsx` рядом с модулем - основное соглашение: тест не потеряется при
переносе компонента, а отсутствие теста заметно. Каталог `__tests__/`
рядом - равноправная альтернатива. Сквозные тесты живут в собственном
каталоге и не попадают в раннер модульных тестов.

## 6.4 Настройка Vitest для React

```sh
npm install --save-dev vitest jsdom @testing-library/react @testing-library/user-event @testing-library/jest-dom msw
```

```ts
// vite.config.ts
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',              // DOM для рендера компонентов
    include: ['src/**/*.test.{ts,tsx}'],
    setupFiles: ['tests/setup.ts'],    // выполняется перед каждым файлом тестов
  },
});
```

```ts
// tests/setup.ts
// Матчеры jest-dom (toBeInTheDocument, toHaveTextContent, toBeDisabled, …) для expect из Vitest
import '@testing-library/jest-dom/vitest';
import { cleanup } from '@testing-library/react';
import { afterEach } from 'vitest';

// Без globals: true Testing Library не видит afterEach и не очищает DOM между тестами сама
afterEach(() => {
  cleanup();
});
```

```json
{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest",
    "test:coverage": "vitest run --coverage"
  }
}
```

| Параметр | Назначение |
| --- | --- |
| `environment: 'jsdom'` | Глобальные `document`, `window`, события; без него `render` падает с `document is not defined`. `happy-dom` быстрее, но менее полон |
| `setupFiles` | Общая подготовка: матчеры, MSW-сервер, очистка. Testing Library сама вызывает `cleanup` после каждого теста, если раннер предоставляет `afterEach` глобально (`globals: true`); иначе - `afterEach(cleanup)` в setup |
| `include` | Какие файлы - тесты |
| `// @vitest-environment node` в первой строке файла | Для тестов без DOM (чистая логика, сервер): быстрее и без побочных эффектов jsdom |

Vitest использует ту же конфигурацию, плагины и алиасы, что и Vite:
компонент с CSS-модулями, SVG и `import.meta.env` тестируется без
дополнительной настройки транспиляции. 🕰️ В Create React App тесты
запускались `react-scripts test` (Jest с предустановленной конфигурацией);
при переезде на Vite замена - Vitest, API `describe`/`it`/`expect` совпадает.

Файл теста:

```tsx
import { describe, test, expect } from 'vitest';
import { render, screen } from '@testing-library/react';
import { Counter } from './counter';

describe('Counter', () => {
  test('shows the initial value', () => {
    render(<Counter initial={5} />);
    expect(screen.getByRole('status')).toHaveTextContent('5');
  });
});
```

`describe` группирует, `test` (синоним `it`) - один сценарий, `expect` -
утверждение. Имя теста читается как предложение о поведении; при падении
раннер печатает путь `Counter > shows the initial value` и разницу
ожидаемого с полученным.
