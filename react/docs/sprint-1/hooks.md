# Хуки

## 1.19 Хуки и их правила

> 📌 **Хук** - функция React с именем, начинающимся с `use`, которая
> подключает функциональный компонент к внутренним механизмам библиотеки
> (состояние, эффекты, контекст, ссылки) и вызывается только во время
> рендера компонента.

Распространенное определение «хуки дают функциональным компонентам
возможности классовых» исторически верно (React 16.8, 2019), но неполно: у
хуков есть то, чего у классов нет, - композиция логики в пользовательских
хуках, `useTransition`, `useSyncExternalStore`.

Встроенные хуки по назначению:

| Группа | Хуки |
| --- | --- |
| Состояние | `useState`, `useReducer` |
| Контекст | `useContext` ([2.2](../sprint-2/context-and-reducer.md#22-контекст)) |
| Ссылки | `useRef`, `useImperativeHandle` |
| Эффекты | `useEffect`, `useLayoutEffect`, `useInsertionEffect`, `useEffectEvent` |
| Производительность | `useMemo`, `useCallback`, `useTransition`, `useDeferredValue` |
| Прочее | `useId`, `useSyncExternalStore`, `useActionState`, `useOptimistic`, `useDebugValue` |

Отдельно от хуков стоит API `use` ([2.39](../sprint-2/react-async.md#239-use-и-suspense)):
оно тоже вызывается только из компонентов и хуков, но, в отличие от хуков,
допускает вызов в условиях и циклах.

### Два правила

1. **Хуки вызываются только на верхнем уровне компонента** - не внутри
   условий, циклов, вложенных функций и не после раннего `return`.
2. **Хуки вызываются только из функциональных компонентов и других хуков** -
   не из обычных функций, обработчиков, классов и модулей.

Правила проверяет ESLint-плагин `eslint-plugin-react-hooks`
(правило `rules-of-hooks`); он входит в стандартные шаблоны проектов.

### Почему порядок вызова фиксирован

React не знает имен переменных состояния. Он хранит данные хуков компонента в
связном списке на внутреннем узле (fiber) и сопоставляет их с вызовами по
**порядковому номеру**: первый `useState` - первая ячейка, второй - вторая,
`useEffect` - третья.

```
   рендер 1                        рендер 2 (тот же порядок)
   ───────────────────────         ───────────────────────
   useState(name)   ──► ячейка 0   useState(name)   ──► ячейка 0  ✅
   useState(age)    ──► ячейка 1   useState(age)    ──► ячейка 1  ✅
   useEffect(sync)  ──► ячейка 2   useEffect(sync)  ──► ячейка 2  ✅

   рендер 2 с хуком внутри условия (условие стало истинным)
   ───────────────────────
   useState(name)   ──► ячейка 0  ✅
   useState(extra)  ──► ячейка 1  ❌ получает данные age
   useState(age)    ──► ячейка 2  ❌ получает данные эффекта
```

Компонент с `useState` внутри `if`, ставшего истинным на втором рендере,
падает с ошибкой `Rendered more hooks than during the previous render`. Если
число хуков не изменилось, а поменялся только порядок, хуки одного типа
молча обмениваются данными, а хук другого типа в чужой ячейке роняет рендер
(`Should have a queue`).

### Пользовательские хуки

> 📌 **Пользовательский хук** - обычная функция с именем `use*`, которая
> вызывает другие хуки; способ вынести логику с состоянием и эффектами из
> компонента и переиспользовать ее.

Каждый вызов пользовательского хука получает собственное состояние: два
компонента с `useFetch(url)` не делят данные, они делят код. Пример хука
`useFetch` - в [1.30](advanced.md#130-компоненты-высшего-порядка-hoc), где
он сравнивается с HOC.

## 1.20 `useEffect`

> 📌 **Побочный эффект** - действие, выходящее за пределы вычисления
> разметки по props и состоянию: запрос к серверу, подписка на событие,
> таймер, ручное изменение DOM, запись в хранилище, логирование.

> 📌 **`useEffect`** - хук, который выполняет переданную функцию после
> коммита рендера и позволяет вернуть из нее функцию очистки; повторный
> запуск управляется массивом зависимостей.

Назначение эффекта - **синхронизация компонента с внешней системой**:
сетью, DOM вне React, таймерами, сторонней библиотекой. Если внешней системы
нет, эффект, скорее всего, не нужен (см. ниже «Когда эффект не нужен»).

### Когда выполняется

```
   рендер ──► коммит DOM ──► отрисовка браузером ──► эффекты
                                                     (очистка предыдущего,
                                                      затем новый)
```

Обычно эффект запускается после того, как браузер показал новый кадр, и не
задерживает отрисовку; эффект, вызванный действием пользователя (нажатием,
вводом), React может выполнить и до нее. Для эффектов, которые обязаны
отработать до отрисовки (измерение размеров и синхронное изменение стилей),
есть `useLayoutEffect` с тем же интерфейсом.

Порядок вызовов для `useEffect(…, [value])` при `value` = 1 → 2 → 2 и
размонтировании: `render 1, effect 1, render 2, cleanup 1, effect 2,
render 2, cleanup 2`. Очистка предыдущего эффекта выполняется перед новым
запуском и при размонтировании; при рендере без изменения зависимостей ни
очистка, ни эффект не запускаются.

### Зависимости

Второй аргумент - массив значений, от которых эффект зависит. React
сравнивает каждый элемент с прошлым рендером по `Object.is` и запускает
эффект, если хотя бы один изменился.

| Вызов | Когда выполняется эффект | Когда выполняется очистка |
| --- | --- | --- |
| `useEffect(fn)` | После каждого рендера | Перед каждым следующим запуском и при размонтировании |
| `useEffect(fn, [])` | Один раз после монтирования | При размонтировании |
| `useEffect(fn, [a, b])` | После монтирования и после рендеров, где изменились `a` или `b` | Перед следующим запуском и при размонтировании |

При последовательности props `{a:1,b:1}` → `{a:1,b:2}` → `{a:2,b:2}` эффект
без массива запускается 3 раза, с `[]` - 1 раз, с `[a]` - 2 раза.

**В массив входят все реактивные значения, которые эффект использует**:
props, состояние, вычисленные из них переменные, функции, объявленные в
компоненте. Правило `exhaustive-deps` того же ESLint-плагина проверяет это.
❌ Пропущенная зависимость - не оптимизация, а устаревшее замыкание: эффект
работает со значениями того рендера, в котором его последний раз запускали.
Если зависимость «мешает», меняется не массив, а код: значение выносится из
эффекта, функция объявляется внутри эффекта, обновление состояния делается
функциональным.

### Функция эффекта - синхронная

Из эффекта возвращается либо ничего, либо функция очистки. `async`-функция
возвращает промис, и React реагирует дважды: предупреждением при
монтировании (`must not return anything besides a function, which is used for
clean-up`) и ошибкой `TypeError: destroy is not a function` при
размонтировании. Асинхронный код объявляется внутри:

```jsx
useEffect(() => {
  let ignore = false;

  async function load() {
    const res = await fetch(`/api/v1/products/${productId}`);
    const data = await res.json();
    if (!ignore) {
      setProduct(data);
    }
  }

  load();

  return () => {
    ignore = true;
  };
}, [productId]);
```

### Гонка запросов и очистка

Эффекты иногда делят на «требующие очистки» (подписки, таймеры) и «не
требующие» (запросы, логирование). Для запросов это деление неверно: если
`productId` сменился дважды, а ответы пришли в обратном порядке, последним
применится ответ на **старый** запрос. Очистка с флагом `ignore` в примере выше
отбрасывает ответы, пришедшие после смены зависимостей: если ответы придут в
порядке «товар 2, товар 1», на экране останется «Товар 2». Тот же результат
дает `AbortController` с `controller.abort()` в очистке - он еще и прерывает
сетевой запрос.

Запись `setState({ ...state, loading: true })` внутри такого эффекта
создает вторую проблему: `state` в замыкании устаревший, и его нет в
зависимостях. Состояние загрузки хранится отдельной переменной или
обновляется функционально.

### `StrictMode`

В режиме разработки `StrictMode` после монтирования выполняет очистку и
запускает эффект повторно: `effect, cleanup, effect`
([1.2](fundamentals.md#12-пакеты-react-и-react-dom-корень-приложения)). Это
не ошибка React, а проверка: эффект с правильной очисткой переживает такой
цикл без последствий (подписка снята и поставлена снова), эффект без
очистки - удваивает подписку и обнаруживается сразу.

### Когда эффект не нужен

| Задача | Вместо эффекта |
| --- | --- |
| Вычислить значение из props или состояния | Вычислить прямо в рендере; для дорогих вычислений - `useMemo` |
| Отреагировать на действие пользователя | Код в обработчике события |
| Сбросить состояние при смене props | `key` на компоненте ([1.14](state-and-lifecycle.md#114-списки-и-key)) |
| Уведомить родителя об изменении состояния | Вызвать callback в том же обработчике, где меняется состояние |
| Цепочка «эффект меняет состояние, второй эффект реагирует» | Одно вычисление в обработчике |

В компоненте может быть несколько эффектов; каждый отвечает за одну
синхронизацию, и делить их по смыслу (подписка отдельно, запрос отдельно)
правильнее, чем собирать в один.

## 1.21 `useMemo` и `useCallback`

> 📌 **Мемоизация** - кеширование результата вычисления по его входным
> данным: при тех же входных данных возвращается сохраненный результат без
> повторного вычисления.

> 📌 **`useMemo(compute, deps)`** - хук, который возвращает результат
> `compute()`, сохраненный с прошлого рендера, пока не изменилась ни одна из
> зависимостей `deps`.

> 📌 **`useCallback(fn, deps)`** - хук, который возвращает ту же самую
> функцию `fn` между рендерами, пока не изменились зависимости;
> эквивалентен `useMemo(() => fn, deps)`.

```jsx
const visibleItems = useMemo(() => filterExpensive(items, query), [items, query]);
const handleSelect = useCallback((id) => onSelect(id, items), [onSelect, items]);
```

### Зачем стабильная ссылка

Каждый рендер компонента объявляет его функции и объекты заново. Само по себе
это дешево. Проблема возникает, когда такая функция или объект:

- передается в потомок, обернутый в `memo`
  ([1.18](state-and-lifecycle.md#118-чистые-компоненты-memo-и-purecomponent)):
  новая ссылка - «изменившийся» prop - рендер потомка: с inline-обработчиком
  потомок в `memo` рендерится вместе с родителем, с `useCallback` - нет;
- входит в зависимости эффекта: новая ссылка - перезапуск эффекта на каждом
  рендере.

### Когда применять

| Ситуация | Решение |
| --- | --- |
| Дорогое вычисление в рендере (замер показывает миллисекунды) | `useMemo` |
| Объект или функция уходит в `memo`-потомок или в зависимости эффекта | `useMemo` / `useCallback` |
| Функция нужна только внутри обработчика или JSX без `memo` | Ничего: обычная функция |
| Проект с React Compiler | Ничего: компилятор мемоизирует сам |

⚠️ `useMemo` - подсказка производительности, а не гарантия: React оставляет
за собой право сбросить кеш (например, при правке файла компонента в
разработке или если компонент приостановился при первом монтировании).
Код должен оставаться корректным и при пересчете.

❌ `useMemo` и `useCallback` «на всякий случай» вокруг каждого значения -
дополнительный код, дополнительная память под кеш и сравнение зависимостей
на каждом рендере без выигрыша.

## 1.22 Ссылки: `useRef`, `createRef` и `forwardRef`

> 📌 **Ссылка (ref)** - объект вида `{ current }`, который сохраняется между
> рендерами компонента и изменение которого не вызывает повторный рендер.

Ссылка - «карман» для данных, не участвующих в разметке. Два применения:
доступ к DOM-узлу и хранение изменяемого значения между рендерами
(идентификатор таймера, экземпляр сторонней библиотеки, предыдущее значение).

| | Состояние | Ссылка |
| --- | --- | --- |
| Изменение вызывает рендер | Да | Нет |
| Чтение в рендере | Да | ❌ Нет (кроме ленивой инициализации) |
| Изменение | Через setter, применяется при следующем рендере | `ref.current = …`, немедленно |
| Значение в текущем рендере | Снимок | Всегда актуальное |

> 📌 **`useRef(initial)`** - хук, который возвращает один и тот же объект
> `{ current: initial }` при каждом рендере компонента.

Два нажатия на кнопку с `ref.current += 1` дают `current === 2` без
повторного рендера; объект ссылки между рендерами один и тот же.

### Ссылка на DOM-узел

```jsx
import { useRef } from 'react';

function InputWithEditButton() {
  const inputRef = useRef(null);

  const handleEdit = () => {
    // current заполнен после коммита: к моменту клика узел уже в DOM
    inputRef.current.focus();
  };

  return (
    <>
      <input type="text" ref={inputRef} />
      <button onClick={handleEdit}>Изменить</button>
    </>
  );
}
```

Атрибут `ref` на DOM-элементе получает объект ссылки; React записывает в
`current` узел при коммите и `null` при удалении узла. Во время первого
рендера `current` еще `null` - поэтому DOM читается в
обработчиках и эффектах, а не в теле компонента.

Когда ссылки на DOM оправданы: управление фокусом, выделением, прокруткой;
воспроизведение медиа; измерение размеров; интеграция со сторонними
DOM-библиотеками (карты, графики). ❌ Чтение `input.value` через ссылку
вместо состояния там, где значение нужно в разметке, - см. управляемые поля
([1.26](events-and-forms.md#126-управляемые-и-неуправляемые-элементы-форм)).

**Callback-ref.** Вместо объекта в `ref` можно передать функцию: React
вызывает ее с узлом при монтировании; с React 19 функция может вернуть
очистку, которая вызывается при удалении узла. Полезно, когда узел нужно
зарегистрировать во внешней системе.

### `createRef`

🕰️ `createRef()` создает объект `{ current: null }` - способ для классовых
компонентов, где хуков нет:

```jsx
class Form extends Component {
  inputRef = createRef();

  componentDidMount() {
    this.inputRef.current.focus();
  }

  render() {
    return <input ref={this.inputRef} />;
  }
}
```

❌ В функциональном компоненте `createRef` создает **новый** объект при
каждом рендере, и сохраненное значение теряется. В функциях - только `useRef`.

### `ref` на компоненте и `forwardRef`

`ref` на DOM-элементе дает узел. А что дает `<FancyInput ref={…} />`, где
`FancyInput` - собственный компонент? До React 19 - ничего: React изымал
`ref` из props, и компонент его не видел. Чтобы «пробросить» ссылку к
внутреннему `<input>`, требовалась обертка `forwardRef`:

```jsx
import { forwardRef } from 'react';

// 🕰️ React ≤18: ref приходит вторым аргументом только внутри forwardRef
const FancyInput = forwardRef(function FancyInput(props, ref) {
  return <input ref={ref} className="fancy" {...props} />;
});
```

✅ С React 19 `ref` - обычный prop функционального компонента:

```jsx
function FancyInput({ ref, ...props }) {
  return <input ref={ref} className="fancy" {...props} />;
}

// Использование одинаково в обоих вариантах
const inputRef = useRef(null);
<FancyInput ref={inputRef} placeholder="Имя" />;
inputRef.current.focus();
```

Оба варианта дают фокус нужному `<input>`. В React 19 `forwardRef` больше не
нужен и работает без предупреждений; документация предупреждает, что в
одной из следующих версий он будет объявлен устаревшим. В новом коде не
используется. Для классовых компонентов `ref` по-прежнему дает экземпляр
класса.

Если наружу нужно отдать не узел, а ограниченный набор методов (`focus`,
`scrollToTop`), применяется `useImperativeHandle(ref, () => ({ … }))` - он
подменяет значение `ref.current` объектом с этими методами.

### Предыдущее значение

Распространенный прием - хранить предыдущее значение props в ссылке,
записывая ее в эффекте без зависимостей и читая в рендере. Он работает, но
нарушает правило «не читать `ref.current` в рендере», и документация React
предлагает решение без эффекта и без ссылки - сравнить с прошлым значением
прямо в рендере:

```jsx
function GameResult({ points }) {
  const [prevPoints, setPrevPoints] = useState(null);
  const [lastPoints, setLastPoints] = useState(points);

  // Предыдущее значение вычисляется прямо в рендере, без эффекта и без ref
  if (points !== lastPoints) {
    setPrevPoints(lastPoints);
    setLastPoints(points);
  }

  return <output>{points}/{prevPoints === null ? '-' : prevPoints}</output>;
}
```

Вызов setter во время рендера допустим только для **собственного** состояния
компонента и только под условием: React немедленно перезапускает рендер с
новым значением, не доходя до коммита. Последовательность `points`
`0 → 5 → 9` дает на экране `9/5`.
