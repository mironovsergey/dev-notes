# Состояние, списки и жизненный цикл

## 1.11 Состояние и `useState`

> 📌 **Состояние (state)** - данные, которые компонент хранит между рендерами
> и изменение которых заставляет React заново отрендерить этот компонент и
> его потомков.

Оба свойства из определения существенны. Обычная переменная в теле компонента
не подходит на роль состояния дважды: она создается заново при каждом вызове
функции, и ее изменение не запускает рендер.

| | Props | Состояние | Локальная переменная |
| --- | --- | --- | --- |
| Откуда | От родителя | Из самого компонента | Из самого компонента |
| Сохраняется между рендерами | Задается заново родителем | Да | Нет |
| Изменение вызывает рендер | Да: новые props приходят с рендером родителя | Да | Нет |
| Кто изменяет | Родитель | Компонент через setter | Кто угодно, без эффекта |

> 📌 **`useState`** - хук, который объявляет одну переменную состояния:
> принимает начальное значение и возвращает пару `[значение, функция-setter]`.
> Вызов setter с новым значением ставит обновление в очередь и планирует
> повторный рендер компонента.

```jsx
import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

При первом рендере `count` равен начальному значению; при каждом следующем -
последнему сохраненному. Функция-setter между рендерами одна и та же
(ее можно безопасно передавать в зависимости эффектов и в дочерние
компоненты). В одном компоненте может быть сколько угодно вызовов `useState`;
как React отличает их друг от друга - в
[1.19](hooks.md#119-хуки-и-их-правила).

### Состояние - снимок рендера

Значение состояния внутри одного рендера не меняется. Обработчик, созданный в
этом рендере, видит значения этого рендера, даже если сработает позже:

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  const handleClick = () => {
    setCount(count + 1);
    // count здесь - значение того рендера, в котором создан обработчик
    setTimeout(() => console.log(count), 0);
  };

  return <button onClick={handleClick}>{count}</button>;
}
```

Два нажатия печатают `0` и `1`, а кнопка показывает `2`. Setter не
изменяет переменную `count` текущего рендера - он просит React выполнить новый
рендер, в котором `count` будет другим.

### Функциональное обновление

Если новое значение зависит от предыдущего, setter принимает функцию:

```jsx
setCount((c) => c + 1);
```

Разница видна при нескольких обновлениях подряд:

```jsx
// Оба вызова видят count === 0 текущего рендера; результат - 1
setCount(count + 1);
setCount(count + 1);

// Функции применяются по очереди к последнему значению; результат - 2
setCount((c) => c + 1);
setCount((c) => c + 1);
```

Если выполнить первый фрагмент, а затем второй, на экране будет `1`, а потом
`3`.

### Пакетирование

> 📌 **Пакетирование (batching)** - объединение нескольких обновлений
> состояния, выполненных в одном обработчике или одной задаче, в один
> рендер.

Три вызова setter в одном обработчике дают один рендер, а не три. С React 18
пакетирование работает везде: в обработчиках событий, в промисах, в
`setTimeout`, в нативных слушателях. 🕰️ В React ≤17 пакетировались только
обновления внутри обработчиков событий React; обновление после `await` или в
`setTimeout` рендерило компонент немедленно.

Из-за очереди и пакетирования `setState` часто называют «асинхронным».
Формулировка неточна: setter не возвращает промис и ничего не
ждет. Точнее так: **обновление ставится в очередь и применяется при
следующем рендере**, поэтому чтение состояния сразу после setter возвращает
старое значение.

### Пропуск рендера при том же значении

Если setter получил значение, равное текущему по `Object.is`, React
пропускает рендер поддерева. ⚠️ Сам компонент при этом иногда вызывается
еще раз, но потомки не рендерятся и коммита не происходит. На это поведение
полагаться нельзя - компонент должен быть чистым.

### Ленивая инициализация

`useState(computeInitial())` вычисляет аргумент при каждом рендере, хотя
используется он только в первом. Для дорогих вычислений передается функция:
`useState(() => computeInitial())` - она вызывается только при первом
рендере.

## 1.12 Неизменяемость состояния

Состояние считается неизменяемым: вместо изменения существующего объекта или
массива создается новый. Причина - способ, которым React решает, изменилось
ли что-то: сравнение по `Object.is`. Мутированный объект - тот же объект, и
для React ничего не произошло:

```jsx
const [items, setItems] = useState(['Раз', 'Два']);

// ❌ мутация: массив тот же, Object.is(items, items) === true, рендера нет
items.push('Три');
setItems(items);

// ✅ новый массив
setItems([...items, 'Три']);
```

После «мутирующего» нажатия в списке по-прежнему два пункта: рендера не
было.

| Операция | Массив | Объект |
| --- | --- | --- |
| Добавить | `[...items, item]` | `{ ...obj, key: value }` |
| Удалить | `items.filter((i) => i.id !== id)` | `const { key, ...rest } = obj` |
| Изменить | `items.map((i) => (i.id === id ? { ...i, done: true } : i))` | `{ ...obj, key: newValue }` |
| Отсортировать | `items.toSorted(compare)` (не `sort`) | - |
| Вложенное | Копируется каждый уровень до изменяемого | Копируется каждый уровень до изменяемого |

Копирование по уровням для глубоких структур утомительно; библиотека Immer
позволяет записать изменение как мутацию черновика и получает новый объект
сама. Второй способ избежать глубоких копий - не хранить глубокие структуры:
держать состояние плоским, со ссылками между записями по идентификатору.

## 1.13 Состояние в классах: `state` и `setState`

🕰️ В классовом компоненте состояние - поле `this.state`, а единственный
способ его изменить - метод `this.setState`.

```jsx
import { Component } from 'react';

class ThemeToggle extends Component {
  state = { theme: 'light', showForm: false };

  handleToggle = () => {
    this.setState((prevState) => ({ showForm: !prevState.showForm }));
  };

  render() {
    return (
      <div className={this.state.theme === 'light' ? 'th-light' : 'th-dark'}>
        <button onClick={this.handleToggle}>{this.state.showForm ? 'Скрыть' : 'Показать'}</button>
      </div>
    );
  }
}
```

Отличия `setState` от setter из `useState`:

| | `this.setState(partial)` | `setValue(next)` |
| --- | --- | --- |
| Объект-аргумент | Сливается с текущим состоянием поверхностно: `setState({ name: 'x' })` сохраняет остальные поля | Заменяет значение целиком: `setForm({ name: 'x' })` теряет остальные поля |
| Функция-аргумент | `(prevState, props) => partial` | `(prev) => next` |
| Второй аргумент | Колбэк, вызываемый после применения обновления | Нет; реакция на изменение - эффект |
| То же значение | Рендер происходит всегда (если не `PureComponent` или `shouldComponentUpdate`) | Рендер поддерева пропускается |

Колбэк второго аргумента демонстрирует очередь обновлений: сразу после
`setState` состояние старое, в колбэке - новое:

```jsx
this.setState({ open: true }, () => console.log(this.state.open)); // true
console.log(this.state.open);                                       // false
```

`forceUpdate` и другие детали классов - в [1.15](#115-классовые-компоненты-в-деталях).

## 1.14 Списки и `key`

Список выводится через `map`, который превращает массив данных в массив
элементов:

```jsx
<ul>
  {items.map((item) => (
    <li key={item.id}>{item.label}</li>
  ))}
</ul>
```

> 📌 **`key`** - строковый или числовой идентификатор элемента среди его
> соседей, по которому React при согласовании сопоставляет элементы
> предыдущего и нового рендера.

Без ключа элементы сопоставляются по позиции: третий с третьим. Пока список
только дописывается в конец, это работает. При удалении первого элемента
позиции сдвигаются: React обновляет каждый узел данными следующего элемента и
удаляет последний, вместо того чтобы удалить первый. Для чистой разметки это
лишняя работа; для элементов с состоянием - ошибка.

### Индекс как ключ

❌ `key={index}` воспроизводит сопоставление по позиции и потому не решает
проблему. Пример: список задач, у каждой - чекбокс со своим состоянием.

```jsx
function Item({ label }) {
  const [checked, setChecked] = useState(false);
  return (
    <li>
      <label>
        <input type="checkbox" checked={checked} onChange={(e) => setChecked(e.target.checked)} />
        {label}
      </label>
    </li>
  );
}

function TodoList() {
  const [items, setItems] = useState([
    { id: 1, label: 'Кофе' },
    { id: 2, label: 'Код' },
  ]);

  return (
    <>
      <button onClick={() => setItems(items.slice(1))}>Удалить первую</button>
      <ul>
        {items.map((item, index) => (
          <Item key={index} label={item.label} /> // ❌ key={index}; ✅ key={item.id}
        ))}
      </ul>
    </>
  );
}
```

Действия: отметить «Кофе», удалить первую задачу. С `key={index}` галочка
оказывается на «Код» - React оставил первый `Item` с его состоянием и лишь
поменял ему `label`. С `key={item.id}` галочка исчезает вместе с задачей.

```
   до удаления            key=index: после          key=id: после
   ┌─────────────┐         ┌─────────────┐          ┌─────────────┐
   │ 0  ☑ Кофе   │  ──►    │ 0  ☑ Код    │  ❌       │ 2  ☐ Код    │  ✅
   │ 1  ☐ Код    │         └─────────────┘          └─────────────┘
   └─────────────┘         (узел 0 остался,         (узел 1 остался,
                            сменился текст)          узел 0 удален)
```

### Требования к ключу

- Уникален среди соседей, не глобально: в разных списках ключи могут
  совпадать.
- Стабилен между рендерами: `key={Math.random()}` - гарантированное
  пересоздание всех элементов на каждом рендере.
- Берется из данных: идентификатор из базы, уникальное поле. Если данные
  ключа не содержат, он назначается один раз при создании записи (например,
  `crypto.randomUUID()`), а не при рендере.
- Индекс допустим только для статического списка: без удаления, вставки в
  середину, сортировки и фильтрации.

`key` не попадает в props компонента; если значение нужно внутри, оно
передается отдельным prop. Из атрибутов фрагмент принимает только `key` и
`ref`, причем только в полной записи `<Fragment key={…}>`; короткая `<>`
атрибутов не допускает.

Смена ключа - способ намеренно сбросить состояние компонента: `<Form
key={userId} />` пересоздает форму при переходе к другому пользователю.

## 1.15 Классовые компоненты в деталях

🕰️ Раздел - для чтения старого кода. В новом коде используются функции.

### Конструктор и привязка `this`

```jsx
import { Component } from 'react';

class SayHi extends Component {
  constructor(props) {
    super(props);
    this.state = { theme: 'dark' };
    // Метод класса не привязан к экземпляру: без bind в обработчике this === undefined
    this.showGreeting = this.showGreeting.bind(this);
  }

  showGreeting() {
    alert(this.props.name);
  }

  render() {
    const className = this.state.theme === 'dark' ? 'btn-dark' : 'btn-light';
    return (
      <button className={className} onClick={this.showGreeting}>
        Нажми на меня
      </button>
    );
  }
}
```

`super(props)` обязателен до обращения к `this` - это правило классов
JavaScript, а не React. Причина `bind`: React вызывает обработчик как обычную
функцию, без объекта-получателя, и `this` внутри метода теряется.

Та же привязка короче через поля класса со стрелочной функцией - стрелка
захватывает `this` лексически, конструктор не нужен:

```jsx
class SayHi extends Component {
  state = { theme: 'dark' };

  showGreeting = () => {
    alert(this.props.name);
  };
  // render как выше
}
```

### `defaultProps`

```jsx
class ImageContainer extends Component {
  static defaultProps = {
    background: 'black',
  };

  render() {
    return <div style={{ background: this.props.background }} />;
  }
}
```

Непереданный `background` получает значение `'black'`. Для классов работает и
в React 19; для функциональных компонентов - нет
([1.8](components.md#18-props)).

### `forceUpdate`

`this.forceUpdate(callback)` запускает рендер в обход `shouldComponentUpdate`
и без изменения состояния. ❌ Потребность в нем означает, что компонент
зависит от данных, которые не лежат ни в props, ни в состоянии; правильное
решение - перенести эти данные в состояние (или подписаться на внешнее
хранилище через `useSyncExternalStore` в функциональном компоненте).

## 1.16 Жизненный цикл классового компонента

🕰️ Методы жизненного цикла существуют только у классов. В функциональных
компонентах те же моменты выражаются эффектами ([1.20](hooks.md#120-useeffect)).

> 📌 **Жизненный цикл компонента** - последовательность этапов от создания
> экземпляра до удаления из DOM: монтирование, обновления, размонтирование, -
> и методы, которые React вызывает на каждом из них.

```
   МОНТИРОВАНИЕ            ОБНОВЛЕНИЕ                      РАЗМОНТИРОВАНИЕ
   ──────────────          ──────────────────────          ────────────────
   constructor             новые props / setState /
        │                  forceUpdate
        ▼                       │
   render                       ▼
        │                  shouldComponentUpdate ─ false ─► (ничего)
        ▼                       │ true
   [коммит DOM]                 ▼
        │                  render
        ▼                       │
   componentDidMount            ▼
                           [коммит DOM]
                                │
                                ▼
                           componentDidUpdate           componentWillUnmount
```

Порядок вызовов: `constructor, render, componentDidMount` при
монтировании; `shouldComponentUpdate, render, componentDidUpdate` при
обновлении; `componentWillUnmount` при удалении.

| Метод | Когда | Для чего |
| --- | --- | --- |
| `constructor(props)` | Один раз до первого рендера | Начальное состояние, привязка методов |
| `render()` | Каждый рендер | Вернуть элементы; чистая функция |
| `componentDidMount()` | После первого коммита | Запросы, подписки, таймеры, обращение к DOM |
| `shouldComponentUpdate(nextProps, nextState)` | Перед каждым повторным рендером | Вернуть `false`, чтобы пропустить рендер |
| `componentDidUpdate(prevProps, prevState)` | После каждого коммита обновления | Реакция на изменение props или состояния - с обязательным сравнением |
| `componentWillUnmount()` | Перед удалением из DOM | Отписки, очистка таймеров, закрытие соединений |
| `static getDerivedStateFromError`, `componentDidCatch` | При ошибке в поддереве | Граница ошибок ([1.28](advanced.md#128-границы-ошибок)) |

### Обновление данных при смене props

```jsx
class Product extends Component {
  state = { product: null, loading: true, hasError: false };

  componentDidMount() {
    this.load();
  }

  componentDidUpdate(prevProps) {
    // Без сравнения запрос уходил бы после каждого рендера, включая рендер после ответа
    if (this.props.productId !== prevProps.productId) {
      this.load();
    }
  }

  load() {
    this.setState({ loading: true, hasError: false });
    fetch(`/api/v1/products/${this.props.productId}`)
      .then((res) => res.json())
      .then((data) => this.setState({ product: data, loading: false }))
      .catch(() => this.setState({ loading: false, hasError: true }));
  }

  render() {
    const { product, loading, hasError } = this.state;
    if (loading) {
      return <p>Загрузка…</p>;
    }
    if (hasError) {
      return <p>Ошибка</p>;
    }
    return <h1>{product.name}</h1>;
  }
}
```

⚠️ Пример содержит типичную для такого кода гонку запросов: ответ на
предыдущий запрос может прийти после ответа на новый и перезаписать его. Решение
для функциональных компонентов - флаг `ignore` в очистке эффекта
([1.20](hooks.md#120-useeffect)); для класса пришлось бы хранить идентификатор
последнего запроса вручную.

### `shouldComponentUpdate`

```jsx
shouldComponentUpdate(nextProps, nextState) {
  // Рендер нужен только при изменении того, что влияет на разметку
  return this.props.tagColor !== nextProps.tagColor || this.state.done !== nextState.done;
}
```

Ручная реализация того, что `PureComponent` делает автоматически
([1.18](#118-чистые-компоненты-memo-и-purecomponent)). Полезна, когда
поверхностного сравнения недостаточно.

### Отписка при размонтировании

```jsx
class VirtualList extends Component {
  state = { offsetY: 0 };

  // Отдельная функция нужна, чтобы removeEventListener получил ту же ссылку
  handleScroll = () => {
    this.setState({ offsetY: window.scrollY });
  };

  componentDidMount() {
    document.addEventListener('scroll', this.handleScroll);
  }

  componentWillUnmount() {
    // Без отписки обработчик продолжит вызывать setState на удаленном компоненте
    document.removeEventListener('scroll', this.handleScroll);
  }
  // render опущен
}
```

### Соответствие хукам

| Класс | Функция |
| --- | --- |
| `constructor` + `this.state` | `useState(initial)` |
| `componentDidMount` | `useEffect(() => { … }, [])` |
| `componentDidUpdate` с сравнением props | `useEffect(() => { … }, [prop])` |
| `componentWillUnmount` | Функция очистки, возвращенная из `useEffect` |
| `shouldComponentUpdate`, `PureComponent` | `memo(Component)` |
| `getDerivedStateFromProps` | Вычисление в рендере или `setState` во время рендера ([1.22](hooks.md#122-ссылки-useref-createref-и-forwardref)) |
| `componentDidCatch` | Нет аналога; класс обязателен |

Соответствие не буквальное: эффект - не «метод жизненного цикла», а
синхронизация с внешней системой ([1.20](hooks.md#120-useeffect)), и один
эффект часто заменяет `componentDidMount` + `componentDidUpdate` +
`componentWillUnmount` вместе.

## 1.17 Подъем состояния

> 📌 **Подъем состояния (lifting state up)** - перенос состояния из
> компонентов, которым оно нужно совместно, в их ближайшего общего предка;
> предок передает значение вниз через props и принимает изменения через
> callback-props.

Нужен в двух случаях: несколько компонентов показывают одни и те же
изменяющиеся данные; один компонент должен изменять данные другого. В обоих
случаях у данных должен быть **единственный источник истины** - один
компонент, который ими владеет.

```jsx
function TemperatureInput({ scale, value, onChange }) {
  return (
    <label>
      {scale === 'c' ? 'Цельсий' : 'Фаренгейт'}
      <input value={value} onChange={(e) => onChange(e.target.value)} />
    </label>
  );
}

function convert(value, from) {
  // Пустое или нечисловое поле не пересчитывается
  if (value.trim() === '' || Number.isNaN(Number(value))) {
    return '';
  }
  const degrees = Number(value);
  return String(Math.round(from === 'c' ? degrees * 9 / 5 + 32 : (degrees - 32) * 5 / 9));
}

function Calculator() {
  // Единственный источник истины - последнее введенное значение и его шкала
  const [input, setInput] = useState({ scale: 'c', value: '' });
  const celsius = input.scale === 'c' ? input.value : convert(input.value, 'f');
  const fahrenheit = input.scale === 'f' ? input.value : convert(input.value, 'c');

  return (
    <>
      <TemperatureInput scale="c" value={celsius} onChange={(value) => setInput({ scale: 'c', value })} />
      <TemperatureInput scale="f" value={fahrenheit} onChange={(value) => setInput({ scale: 'f', value })} />
    </>
  );
}
```

Хранится только последнее введенное значение и его шкала; второе поле
вычисляется. Если хранить оба числа, они рано или поздно разойдутся - это и
есть избыточное состояние, которого избегает шаг 3 из
[1.7](components.md#17-декомпозиция-и-композиция). Ввод `100` в первое поле
дает `212` во втором; ввод `32` во второе - `0` в первом. Введенное значение
остается в своем поле как есть: если бы хранились только градусы Цельсия,
округление переписывало бы ввод во втором поле (33 ℉ → 1 ℃ → 34 ℉).

Компонент `TemperatureInput` после подъема стал **управляемым**
([1.26](events-and-forms.md#126-управляемые-и-неуправляемые-элементы-форм)):
у него нет собственного состояния, значение и его изменение приходят сверху.

## 1.18 Чистые компоненты: `memo` и `PureComponent`

Рендер родителя по умолчанию рендерит всех потомков, независимо от того,
изменились ли их props. Для большинства компонентов это дешево. Когда потомок
дорог, а его props меняются редко, лишний рендер можно пропустить.

> 📌 **`memo`** - функция, возвращающая обертку над компонентом, которая
> при повторном рендере родителя пропускает рендер компонента, если его props
> не изменились по поверхностному сравнению.

> 📌 **Поверхностное сравнение (shallow equal)** - сравнение двух объектов
> по первому уровню: одинаковый набор ключей и `Object.is` для каждого
> значения; вложенные объекты по содержимому не сравниваются.

```jsx
import { memo } from 'react';

const Chat = memo(function Chat({ id, lastMessageAt }) {
  return (
    <div className="chat">
      <img src={`img/${id}.png`} alt="" />
      <div className="date">{lastMessageAt}</div>
    </div>
  );
});
```

После двух нажатий на кнопку родитель отрендерен трижды, обычный потомок -
тоже трижды, потомок в `memo` - один раз.

⚠️ Поверхностное сравнение ломается на значениях, создаваемых в рендере
заново: `<Chat style={{ color: 'red' }} />` - каждый рендер новый объект,
`Object.is` дает `false`, `memo` бесполезен. То же с
функциями-обработчиками; решение - `useMemo` и `useCallback`
([1.21](hooks.md#121-usememo-и-usecallback)).

Второй аргумент `memo(Component, arePropsEqual)` задает собственное
сравнение; нужен редко.

🕰️ **`PureComponent`** - базовый класс, реализующий `shouldComponentUpdate`
поверхностным сравнением props и состояния. Обычный класс после `setState`
с тем же значением рендерится повторно, `PureComponent` - нет.

```jsx
import { PureComponent } from 'react';

class Chat extends PureComponent {
  render() {
    // тот же JSX, что выше
  }
}
```

❌ Проверять работу `memo` выводом `Math.random()` в разметке - нарушение
чистоты рендера: компонент с таким кодом непредсказуем и в `StrictMode`
покажет разные числа при одинаковых props. Число рендеров считается в тесте
или в React DevTools Profiler.

### Когда применять

- Сначала измерение (React DevTools Profiler), потом `memo`. Само сравнение
  props тоже стоит времени; для дешевого компонента `memo` - чистые издержки.
- Лучший способ избежать лишних рендеров - структура: состояние живет как
  можно ниже, а дорогие поддеревья передаются через `children` и не зависят
  от изменившегося состояния.
- **React Compiler** (стабильная версия 1.0, 2025) расставляет мемоизацию
  автоматически при условии, что код соблюдает правила React (чистота,
  неизменяемость). В проекте с компилятором ручной `memo` нужен как
  исключение.
