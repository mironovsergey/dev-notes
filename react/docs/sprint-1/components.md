# Компоненты и props

## 1.6 Компонент

> 📌 **Компонент** - функция (или класс с методом `render`), которая
> принимает единственный аргумент - объект `props` - и возвращает описание
> части интерфейса: элементы React, строку, число, массив таких значений или
> `null`. Имя компонента начинается с заглавной буквы.

Компонент - это тип элемента ([1.3](fundamentals.md#13-элемент-react)): в
`<UserGreeting fullName="Анна" />` поле `type` элемента - сама функция
`UserGreeting`, а `props` - `{ fullName: 'Анна' }`. При рендере React вызывает
функцию с этими props и получает поддерево.

### Функциональный компонент

```jsx
function UserGreeting({ fullName }) {
  return <h1>Здравствуйте, {fullName}</h1>;
}
```

✅ Единственная форма для нового кода. Состояние и побочные эффекты
подключаются хуками ([1.19](hooks.md#119-хуки-и-их-правила)).

### Классовый компонент

```jsx
import { Component } from 'react';

class UserGreeting extends Component {
  render() {
    return <h1>Здравствуйте, {this.props.fullName}</h1>;
  }
}
```

🕰️ Классы поддерживаются в React 19 и не объявлены устаревшими, но
документация относит их API к устаревшим (legacy): хуки в классах недоступны,
новые возможности (Actions, `use`) рассчитаны на функции. Единственная задача,
для которой класс по-прежнему обязателен, - граница ошибок
([1.28](advanced.md#128-границы-ошибок)). Устройство классов разобрано в
[1.15](state-and-lifecycle.md#115-классовые-компоненты-в-деталях) и
[1.16](state-and-lifecycle.md#116-жизненный-цикл-классового-компонента) -
для чтения старого кода.

### Чистота

Компонент - функция в математическом смысле: при одних и тех же props и
состоянии возвращает одно и то же описание и не делает ничего сверх этого.
React вызывает ее тогда и столько раз, сколько считает нужным, в том числе
дважды подряд в `StrictMode`
([1.2](fundamentals.md#12-пакеты-react-и-react-dom-корень-приложения)). Код,
который в рендере отправляет запрос, пишет в глобальную переменную или
изменяет DOM, ломается непредсказуемо. Место побочных эффектов - обработчики
событий ([1.25](events-and-forms.md#125-обработчики-событий-в-компонентах)) и
эффекты ([1.20](hooks.md#120-useeffect)).

### Заглавная буква

`<greeting />` компилятор JSX превращает в строку `'greeting'`, то есть в
неизвестный DOM-тег; `<Greeting />` - в ссылку на функцию. Запись через точку
(`<ui.Button />`) всегда компилируется в обращение к свойству объекта,
независимо от регистра.

### Объявление на уровне модуля

❌ Компонент, объявленный внутри другого компонента, пересоздается на каждом
рендере родителя. Для React это каждый раз новый тип элемента, и по правилу
согласования ([1.4](fundamentals.md#14-virtual-dom-и-согласование)) старое
поддерево удаляется вместе с состоянием:

```jsx
function PanelBroken() {
  const [tick, setTick] = useState(0);

  // ❌ на каждом рендере PanelBroken это новая функция, то есть новый тип элемента
  function Counter() {
    const [count, setCount] = useState(0);
    return <button onClick={() => setCount((c) => c + 1)}>count {count}</button>;
  }

  return (
    <div>
      <Counter />
      <button onClick={() => setTick((t) => t + 1)}>tick {tick}</button>
    </div>
  );
}
```

Два нажатия на счетчик дают `count 2`, одно нажатие на `tick` - и счетчик
показывает `count 0`. С `Counter`, вынесенным на уровень модуля,
после тех же действий остается `count 2`.

## 1.7 Декомпозиция и композиция

> 📌 **Декомпозиция** - разбиение интерфейса на компоненты, каждый из
> которых отвечает за одну обособленную часть разметки и связанной с ней
> логики.

> 📌 **Композиция** - сборка сложных компонентов из более простых через
> вложение в разметке и передачу через props (в том числе `children`), а не
> через наследование.

Компоненты ссылаются на другие компоненты в возвращаемом дереве, поэтому одна
и та же абстракция работает на любом уровне: кнопка, форма, страница,
приложение - все это компоненты.

### Когда выделять компонент

- Фрагмент разметки повторяется в двух и более местах. Правка в одном месте
  должна применяться ко всем.
- Компонент разросся настолько, что его код не помещается на экран и его
  трудно читать; в нем можно назвать несколько независимых частей.
- Часть интерфейса имеет собственное состояние или логику, не нужную
  соседям.

### Порядок работы над новым интерфейсом

Схема из документации React («Thinking in React»):

1. Разбить макет на иерархию компонентов - по принципу единственной
   ответственности: один компонент делает одну вещь.
2. Собрать статическую версию без состояния: компоненты получают данные
   через props сверху вниз.
3. Найти минимальное состояние: все, что вычисляется из других данных или
   props, состоянием не является ([1.11](state-and-lifecycle.md#111-состояние-и-usestate)).
4. Определить, где состояние живет: в ближайшем общем предке всех компонентов,
   которым оно нужно ([1.17](state-and-lifecycle.md#117-подъем-состояния)).
5. Добавить обратный поток: дочерние компоненты сообщают об изменениях через
   callback-props.

Для интернет-магазина иерархия первого шага может быть такой:

```
   App
   ├── Header
   │   ├── Search
   │   └── CartButton
   ├── Catalog
   │   ├── Filter
   │   └── ProductCard  ×N
   │       ├── Price
   │       └── AddToCartButton
   └── Footer
```

### Композиция вместо наследования

Иерархии наследования компонентов React не рекомендует: общее поведение
выносится в отдельный компонент, хук ([1.19](hooks.md#119-хуки-и-их-правила))
или функцию, варианты одного компонента выражаются props, а вложенное
содержимое передается через `children` ([1.9](#19-children)).

## 1.8 Props

> 📌 **Props (свойства)** - входные данные компонента: объект, который React
> собирает из атрибутов JSX и вложенного содержимого и передает компоненту
> единственным аргументом. Компонент только читает props; изменить их может
> только родитель, передав новые значения при следующем рендере.

Props - аналог аргументов функции, и поток данных через них
**однонаправленный**: сверху вниз, от родителя к потомку. Если потомку нужно
что-то изменить «наверху», родитель передает ему функцию, и потомок ее
вызывает ([1.17](state-and-lifecycle.md#117-подъем-состояния)).

**Только чтение.** В режиме разработки объект `props` заморожен; присваивание
`props.name = 'x'` дает `TypeError: Cannot assign to read only property`.
Причина та же, что у неизменяемости элементов: React сравнивает старые и
новые props, и они должны оставаться такими, какими были переданы.

### Деструктуризация и значения по умолчанию

```jsx
function Greeting({ name, role = 'гость' }) {
  return <p>Здравствуйте, {name} ({role})</p>;
}

<Greeting name="Анна" />              // Здравствуйте, Анна (гость)
<Greeting name="Анна" role="админ" /> // Здравствуйте, Анна (админ)
```

✅ Значение по умолчанию задается в деструктуризации. Оно применяется, когда
prop не передан или передан как `undefined`; `null` умолчанием не заменяется.
🕰️ `Component.defaultProps = { … }` для функциональных компонентов в React 19
игнорируется без предупреждения; для классов работает
([1.15](state-and-lifecycle.md#115-классовые-компоненты-в-деталях)).

### Передача spread-оператором

```jsx
function Profile({ userId, ...rest }) {
  // userId нужен только этому компоненту, остальное уходит во вложенный Avatar
  return <Avatar {...rest} />;
}

function Avatar({ src, size }) {
  return <img src={src} width={size} height={size} alt="" />;
}

<Profile userId={7} src="a.png" size={32} />
```

`{...rest}` уместен для оберток, которые пробрасывают props дальше без
изменений. Цена: интерфейс компонента перестает быть виден по его сигнатуре,
а лишние props, дошедшие до DOM-элемента, дают предупреждения о
неизвестных атрибутах. ❌ `<Card {...props} />` по умолчанию во всех
компонентах - признак, что границы компонентов проведены неверно.

### Слишком много props

Десяток props у одного компонента - сигнал к декомпозиции
([1.7](#17-декомпозиция-и-композиция)): либо компонент делает слишком много,
либо связанные props стоит объединить в объект, либо часть содержимого
передать как `children`:

```jsx
<OrderContent>
  <OrderInfo time="25.09.2021 14:33:24" orderId="ADF-21244324-11" />
  <Customer {...customer} />
  <Products data={products} />
  <Address coords={[56.033661, 37.859848]} name="ул. 26 Бакинских Комиссаров, 11" />
  <OrderTotal value={1293.3} />
</OrderContent>
```

`OrderContent` не знает, из чего состоит заказ; он задает только каркас.

### Проброс props

> 📌 **Проброс props (props drilling)** - передача данных через несколько
> уровней компонентов, которым сами данные не нужны, только чтобы доставить
> их глубже.

Два-три уровня - нормально. Когда промежуточных компонентов много, решения
два: композиция (передать готовый элемент через `children`, чтобы
промежуточные уровни его не разбирали) и контекст
([2.2](../sprint-2/context-and-reducer.md#22-контекст)).

## 1.9 `children`

> 📌 **`children`** - специальный prop, в который попадает содержимое между
> открывающим и закрывающим тегами компонента. Тип - любое отображаемое
> значение: элемент, строка, массив, `null`.

```jsx
function Card({ title, children }) {
  return (
    <section className="card">
      <h2>{title}</h2>
      {children}
    </section>
  );
}

<Card title="Заказ">
  <p>Оплачен</p>
</Card>
// <section class="card"><h2>Заказ</h2><p>Оплачен</p></section>
```

`children` - основной инструмент композиции: компонент-обертка (карточка,
модальное окно, раскладка страницы) не знает, что внутри, и не должен знать.
Если «слотов» несколько, остальные передаются обычными props с элементами:
`<Layout sidebar={<Menu />}>…</Layout>`.

🕰️ Утилиты `Children.map`, `Children.count`, `Children.only` из пакета `react`
позволяют перебирать `children` как массив. Документация не рекомендует их:
код становится хрупким - обертка `<Fragment>` или условный `null` меняют
результат перебора. Вместо этого данные передаются массивом, а разметка -
функцией (render prop) или готовыми элементами.

## 1.10 Проверка типов: PropTypes и TypeScript

🕰️ **`prop-types`** - отдельная библиотека, описывающая ожидаемые типы props
объектом `Component.propTypes`; проверка выполнялась только в режиме
разработки и выводила предупреждение в консоль:

```jsx
import PropTypes from 'prop-types';

function OrderNumber({ orderId }) {
  return <span>Номер заказа: {orderId}</span>;
}

OrderNumber.propTypes = {
  orderId: PropTypes.number,
};

<OrderNumber orderId="1138" /> // React ≤18: предупреждение о типе; React 19: ничего
```

В React 19 проверка `propTypes` удалена: объект игнорируется, предупреждений
нет - и у функциональных компонентов, и у классов.

✅ Роль проверки типов перешла к TypeScript: типы props описываются
интерфейсом, а ошибка обнаруживается при компиляции, а не в консоли браузера.
Типизация компонентов разбирается в спринте 4.

| | PropTypes | TypeScript |
| --- | --- | --- |
| Когда проверяет | Во время выполнения, только в разработке | При компиляции, всегда |
| Что проверяет | Тип переданного значения | Тип значения и его использование внутри компонента |
| Статус в React 19 | Игнорируется | Рекомендуемый способ |
