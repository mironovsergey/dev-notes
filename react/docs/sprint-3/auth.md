# Безопасность: аутентификация и авторизация

## 3.9 Идентификация, аутентификация, авторизация

> 📌 **Идентификация** - предъявление идентификатора: имени пользователя,
> e-mail, номера телефона. Отвечает на вопрос «кто ты?».

> 📌 **Аутентификация** - проверка, что предъявивший идентификатор
> действительно тот, за кого себя выдает: пароль, код из SMS, ключ,
> биометрия. Отвечает на вопрос «докажи».

> 📌 **Авторизация** - выдача прав: решение, какие действия и данные
> доступны аутентифицированному пользователю. Отвечает на вопрос «что тебе
> можно?».

```
   идентификация ──► аутентификация ──► авторизация
   «я anna@mail»      «пароль верный»    «anna - редактор: может писать,
                                          не может удалять»
```

Идентификация - часть аутентификации; авторизация возможна только после
нее. Разделение имеет практический смысл: ошибка «неверный пароль» - отказ
в аутентификации (HTTP 401 Unauthorized), а «нет доступа к этому разделу» -
отказ в авторизации (HTTP 403 Forbidden). Клиент реагирует на них по-разному:
на 401 - показать форму входа, на 403 - сообщить об отсутствии прав.

HTTP не хранит состояние: каждый запрос для сервера независим. Чтобы не
вводить пароль на каждый запрос, после аутентификации клиент получает
**удостоверение**, которое предъявляет дальше. Удостоверение бывает двух
видов - токен и идентификатор сессии.

## 3.10 Токены и JWT

> 📌 **Токен доступа (access token)** - строка, которую сервер выдает после
> аутентификации и которую клиент прикладывает к каждому запросу как
> доказательство того, что аутентификация пройдена.

```
   1. клиент ──► POST /login { email, password }
   2. сервер проверяет пароль, выдает токен ──► клиент
   3. клиент сохраняет токен (cookie или память)
   4. клиент ──► GET /api/user   Authorization: Bearer <token>
   5. сервер проверяет токен, отвечает данными
   6. выход: клиент удаляет токен; сервер при необходимости помечает токен отозванным
```

Токен передается в заголовке `Authorization` со схемой `Bearer`
(«предъявитель»): схема сообщает серверу, как трактовать значение.

### JWT

> 📌 **JWT (JSON Web Token)** - стандарт токена из трех частей, разделенных
> точками: заголовок и полезная нагрузка - JSON в кодировке base64url,
> третья часть - подпись заголовка и нагрузки секретным ключом сервера.

```
   eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiIzOWRvdzhhayIsIm5hbWUiOiJNci4gU21pdGgiLCJleHAiOjE4MDAwMDAwMDB9 . 6TOTd…
   ──────────── header ─────────────────   ───────────────────────────── payload ─────────────────────────────   ─ signature ─
   {"alg":"HS256","typ":"JWT"}             {"sub":"39dow8ak","name":"Mr. Smith","exp":1800000000}                HMAC-SHA256(header.payload, secret)
```

| Часть | Содержимое |
| --- | --- |
| `header` | Алгоритм подписи (`HS256` - симметричный HMAC, `RS256` - асимметричный RSA) и тип |
| `payload` | Утверждения (claims): `sub` - идентификатор пользователя, `exp` - срок действия, `iat` - время выдачи, произвольные поля (роль, имя) |
| `signature` | Подпись первых двух частей; вычислить или проверить ее можно только с ключом |

Что из этого следует:

- **Нагрузка читается кем угодно.** base64url - кодировка, а не
  шифрование: имя и `sub` из примера декодируются без всякого ключа.
  ❌ Пароли, персональные данные, секреты в JWT не кладутся.
- **Подмена обнаруживается.** Изменить нагрузку (`"name":"Hacker"`) можно,
  но подпись перестанет сходиться.
- **Сервер ничего не хранит.** Проверка - вычисление подписи и сравнение
  `exp` с текущим временем; база не нужна. Поэтому один токен принимают
  несколько серверов и API работает с любыми клиентами - браузером,
  мобильным приложением, другим сервером.
- ⚠️ **Отозвать токен нельзя.** Раз сервер ничего не хранит, выданный
  токен действует до `exp`, даже если пользователь вышел или сменил пароль.
  Поэтому срок жизни access-токена делают коротким (минуты), а для
  продления выдают **refresh-токен** с длинным сроком, который хранится
  строже и проверяется по базе. Это компромисс между «без состояния» и
  «можно отозвать».

Клиенту содержимое токена обычно не нужно: он хранит строку и
прикладывает к запросам. Читать `exp` на клиенте допустимо, чтобы обновить
токен заранее; доверять содержимому - нет: решение принимает сервер.

## 3.11 Сессии, cookie и хранение токена

> 📌 **Сессия** - запись на сервере (в памяти, файле или базе) с данными
> аутентифицированного пользователя; клиент хранит только ее идентификатор,
> который сервер выдает в cookie и получает обратно с каждым запросом.

```
   1. клиент ──► POST /login
   2. сервер создает запись сессии, отвечает
      Set-Cookie: sid=a1b2…; HttpOnly; Secure; SameSite=Lax
   3. браузер сам прикладывает Cookie: sid=a1b2… к каждому запросу на этот домен
   4. сервер находит сессию по sid ──► пользователь известен
   5. выход: сервер удаляет запись; cookie становится бесполезной
```

| | Сессии | Токены (JWT) |
| --- | --- | --- |
| Состояние на сервере | Есть: запись на каждую сессию | Нет: проверка подписью |
| Отзыв | Мгновенный: удалить запись | Только по истечении `exp` (или через refresh и черный список) |
| Масштабирование | Общее хранилище сессий для всех серверов | Любой сервер с ключом |
| Клиенты | Браузеры: механизм cookie | Любые |
| Передача | Cookie автоматически | Заголовок `Authorization` вручную (или cookie) |
| Уязвимость по умолчанию | CSRF: браузер шлет cookie и по чужому запросу | XSS: скрипт читает токен из `localStorage` |

Оба подхода живы; выбор зависит от того, кто клиенты и нужен ли мгновенный
отзыв.

### Cookie

> 📌 **Cookie** - небольшая (до 4 КБ) пара «имя=значение», которую сервер
> устанавливает заголовком `Set-Cookie` (или скрипт - через
> `document.cookie`), браузер хранит и автоматически отправляет с каждым
> запросом к домену cookie.

Атрибуты, определяющие безопасность:

| Атрибут | Что делает |
| --- | --- |
| `HttpOnly` | Cookie недоступна из JavaScript - `document.cookie` ее не показывает; защита от кражи через XSS. Установить можно только с сервера |
| `Secure` | Отправляется только по HTTPS |
| `SameSite=Strict \| Lax \| None` | Отправлять ли cookie с запросов, инициированных другим сайтом; `Lax` и `Strict` закрывают большинство CSRF; значение по умолчанию зависит от браузера, поэтому атрибут задают явно |
| `Expires` / `Max-Age` | Срок жизни; без них - до закрытия браузера |
| `Path`, `Domain` | Для каких адресов отправлять |

Утилиты для работы с `document.cookie` со стороны клиента:

```js
/**
 * Записывает cookie. expires - число секунд или объект Date; остальные атрибуты
 * (path, secure, samesite) передаются как есть.
 */
export function setCookie(name, value, options = {}) {
  const props = { path: '/', ...options };
  let { expires } = props;

  if (typeof expires === 'number') {
    const date = new Date();
    date.setTime(date.getTime() + expires * 1000);
    expires = date;
  }
  if (expires instanceof Date) {
    props.expires = expires.toUTCString();
  }

  let cookie = `${name}=${encodeURIComponent(value)}`;
  for (const [key, val] of Object.entries(props)) {
    cookie += `; ${key}`;
    if (val !== true) {
      cookie += `=${val}`;
    }
  }
  document.cookie = cookie;
}

export function getCookie(name) {
  const matches = document.cookie.match(
    new RegExp(`(?:^|; )${name.replace(/([.$?*|{}()[\]\\/+^])/g, '\\$1')}=([^;]*)`)
  );
  return matches ? decodeURIComponent(matches[1]) : undefined;
}

export function deleteCookie(name) {
  // Отрицательный срок жизни заставляет браузер удалить cookie немедленно
  setCookie(name, '', { expires: -1 });
}
```

`document.cookie` - одна строка со всеми доступными cookie через `; `,
поэтому чтение требует разбора; экранирование имени в регулярном выражении
защищает от спецсимволов.

### Где хранить токен на клиенте

| Хранилище | Читается скриптом (XSS) | Уходит автоматически (CSRF) | Переживает перезагрузку |
| --- | --- | --- | --- |
| Cookie `HttpOnly; Secure; SameSite` | Нет - безопаснее всего | Да, но `SameSite` ограничивает | Да |
| Cookie через `document.cookie` | Да | Да | Да |
| `localStorage` | Да | Нет | Да |
| Память приложения (переменная, стор) | Только во время работы | Нет | ❌ Нет: после перезагрузки нужен повторный вход или refresh |

✅ Рекомендуемая схема: токен в `HttpOnly`-cookie, которую ставит сервер, -
клиентский код токена не видит и передавать ничего не должен. Если API
принимает токен только в заголовке `Authorization`, токен читают из обычной
cookie или держат в памяти, а восстанавливают через refresh-запрос.
`localStorage` для токенов - наименее защищенный вариант: любой сработавший
XSS получает его одной строкой.

Извлечение токена из ответа на вход зависит от API: тело ответа
(`{ accessToken }`) или заголовок `Authorization: Bearer …`
(`res.headers.get('authorization')`).
Хранится только сам токен, без схемы `Bearer` - схема добавляется при
отправке.

## 3.12 Защищенные маршруты и выход

> 📌 **Защищенный маршрут** - маршрут, доступный только пользователю с
> нужным состоянием авторизации; для остальных вместо страницы выполняется
> редирект (на вход) или показывается отказ.

⚠️ Защита на клиенте - удобство, а не безопасность: код страницы в любом
случае доступен в бандле, а данные защищает сервер, проверяя токен на
каждом запросе. Клиентская проверка нужна, чтобы не показывать пустой
экран и не отправлять заведомо неавторизованные запросы.

### Компонент-обертка

```jsx
import { useContext } from 'react';
import { Navigate, useLocation } from 'react-router';

function ProtectedRoute({ children }) {
  const { user, isLoaded } = useContext(AuthContext);
  const location = useLocation();

  if (!isLoaded) {
    // Пока статус не известен, редирект был бы преждевременным: пользователь уже вошел,
    // но getUser еще не завершился
    return <p>Проверка…</p>;
  }
  if (!user) {
    // Исходный адрес сохраняется, чтобы после входа вернуть на него пользователя
    return <Navigate to="/login" state={{ from: location }} replace />;
  }
  return children;
}

<Route path="/settings" element={<ProtectedRoute><Settings /></ProtectedRoute>} />
```

Три состояния - «проверка», «не вошел», «вошел» - обязательны все три:
без первого пользователь с действующим токеном при каждой перезагрузке на
мгновение видит форму входа или уходит на нее насовсем.

Страница входа читает `location.state.from` и возвращает пользователя туда,
откуда его перенаправили:

```jsx
import { useContext } from 'react';
import { useLocation, useNavigate } from 'react-router';

function LoginPage() {
  const { signIn } = useContext(AuthContext);
  const navigate = useNavigate();
  const location = useLocation();
  const from = location.state?.from?.pathname ?? '/';

  const handleSubmit = async (e) => {
    e.preventDefault();
    await signIn(new FormData(e.currentTarget));
    navigate(from, { replace: true }); // replace: страница входа не остается в истории
  };

  return (
    <form onSubmit={handleSubmit}>
      <h1>Вход</h1>
      <label>E-mail<input name="email" type="email" /></label>
      <label>Пароль<input name="password" type="password" /></label>
      <button type="submit">Войти</button>
    </form>
  );
}
```

🕰️ В версии 5 обертка рендерила `<Route {...rest} render={({ location }) =>
user ? children : <Redirect to={{ pathname: '/login', state: { from:
location } }} />} />`. С версии 6 `Route` не оборачивается - защищается
`element`.

Если защищенных маршрутов много, обертка ставится один раз на
layout-маршрут ([3.5](react-router.md#35-конфигурация-маршрутов)):
`<Route element={<ProtectedRoute><Outlet /></ProtectedRoute>}>` - все
вложенные маршруты защищены.

### Редирект в `loader`

В data-режиме проверка выполняется **до** рендера, и промежуточное состояние
не нужно:

```jsx
import { redirect } from 'react-router';

{
  path: 'settings',
  loader: async () => {
    const user = await getUser();
    if (!user) {
      throw redirect('/login');
    }
    return { user };
  },
  Component: Settings,
}
```

### Контекст авторизации

Состояние `user`, `isLoaded` и функции `signIn`, `signOut` живут в одном
месте - контексте ([2.2](../sprint-2/context-and-reducer.md#22-контекст))
или сторе - и читаются хуком `useAuth()`. `getUser` вызывается один раз при
старте приложения (проверить сохраненный токен), а не в каждом защищенном
маршруте.

### Выход

1. Запрос на сервер (`POST /logout`): для сессий - удалить запись, для
   токенов - отозвать refresh-токен.
2. Очистить состояние приложения: `user`, кеши данных пользователя.
3. Удалить токен из хранилища (`deleteCookie('token')`); `HttpOnly`-cookie
   удаляет сервер заголовком `Set-Cookie` с прошедшей датой.
4. Перейти на публичную страницу с `replace`, чтобы «назад» не возвращал в
   кабинет.
