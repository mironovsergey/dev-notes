# Вероятностный анализ алгоритмов

[← К содержанию спринта](README.md)

Здесь аппарат предыдущих тем применяется к задачам, где случайность возникает
не из условия, а из самого алгоритма или из потока данных. Все пять сюжетов
решаются одними и теми же средствами - линейностью ожидания, методом
индикаторов и разложением на геометрические слагаемые, - и все пять дают
ответы, расходящиеся с интуицией: совпадение наступает после `√n` шагов, а не
после `n/2`, а покрытие всех значений требует `n ln n` попыток, а не `n`.

---

## 4.7 Вероятностный анализ алгоритмов

### 4.7.1 Парадокс дней рождения

Из `n` равновероятных значений независимо выбираются `k`. Вероятность, что
все они различны, считается
[цепным правилом](conditional.md#421-определение-условной-вероятности-теорема-умножения):

```
   P(все различны) = (1 − 1/n)(1 − 2/n) ... (1 − (k−1)/n)
```

Логарифмирование и оценка `ln(1 − x) ≈ −x` при малых `x` дают

```
   P(все различны) ≈ exp( −k(k−1) / (2n) ) ≈ exp( −k² / (2n) )
```

Вероятность совпадения достигает `1/2`, когда показатель равен `−ln 2`:

```
   k ≈ √(2n · ln 2) ≈ 1.177 · √n
```

**Порог линеен по `√n`, а не по `n`** - в этом весь парадокс. Для `n = 365`
формула дает `k ≈ 22.5`, точный расчет - 23 человека для вероятности `0.507`
и 57 человек для `0.99`.

| Разрядность хеша | `n` | Порог `≈ 1.177√n` |
| --- | --- | --- |
| 32 бита | `4.3 · 10⁹` | `≈ 77 · 10³` |
| 64 бита | `1.8 · 10¹⁹` | `≈ 5.1 · 10⁹` |
| 128 бит | `3.4 · 10³⁸` | `≈ 2.2 · 10¹⁹` |

Практический вывод: 32-битный хеш сталкивается с коллизией уже на сотне тысяч
объектов, поэтому для идентификаторов он непригоден. Именно этот расчет
определяет выбор длины хеша и длину сокращенных идентификаторов коммитов, а
также лежит в основе атаки «дней рождения» на криптографические хеш-функции:
подбор коллизии стоит `2^(b/2)`, а не `2^b` операций.

Разбор коллизий с точки зрения реализации - в
[хеш-функциях](../../../algorithms/docs/sprint-4/collisions.md) и
[хешировании строк](../../../algorithms/docs/sprint-4/string-hashing.md).

### 4.7.2 Задача о собирателе купонов

Существует `n` различных купонов; каждый раз выпадает равновероятный. Сколько
покупок нужно, чтобы собрать все?

Пусть `T` - общее число покупок, `Tᵢ` - число покупок для получения `i`-го
нового купона после того, как собрано `i − 1`. Когда собрано `i − 1` купонов,
вероятность получить новый равна `(n − i + 1)/n`, поэтому `Tᵢ` имеет
[геометрическое распределение](distributions.md#452-геометрическое-распределение)
с ожиданием `n / (n − i + 1)`. По линейности:

```
   E T = Σ n/(n − i + 1) = n · (1/n + 1/(n−1) + ... + 1/1) = n · Hₙ

   E T = n·Hₙ ≈ n·ln n + γn,   γ ≈ 0.5772
```

Слагаемые сильно неравноправны: первая половина купонов набирается примерно
за `0.7n` покупок, а последний купон требует в среднем `n` покупок сам по
себе. «Длинный хвост» и создает множитель `ln n`.

```
   n = 100:    E T = 100 · H₁₀₀ ≈ 519
   n = 1000:   E T ≈ 7485
```

Концентрация оценивается неравенством Буля: вероятность не собрать все
купоны за `n ln n + cn` шагов не превосходит `e^(−c)`. Иными словами,
превышение среднего более чем на несколько `n` практически исключено.

Схема возникает всюду, где требуется покрыть все варианты случайными
пробами: прогрев кеша, покрытие ветвей случайным тестированием, ожидание
опроса всех узлов при случайном выборе. Общее правило - **покрытие стоит
`n ln n`, а не `n`**.

### 4.7.3 Ожидаемая длина цепочки в хеш-таблице

`m` ключей размещаются в `n` ячейках хеш-таблицы с разрешением коллизий
цепочками. В предположении простого равномерного хеширования каждый ключ
попадает в каждую ячейку с вероятностью `1/n` независимо от остальных.

Длина цепочки в ячейке `j` - сумма индикаторов попадания, поэтому

```
   E(длина цепочки) = m/n = α        α - коэффициент заполнения
```

Отсюда стандартные оценки поиска:

```
   неудачный поиск:  1 + α
   удачный поиск:    1 + α/2
```

Обе величины равны `O(1)` при постоянном `α`, что и обосновывает
[хеш-таблицы](../../../algorithms/docs/sprint-4/hash-tables.md) как структуру
с ожидаемым постоянным временем операций. Существенно, что оценка -
**ожидание**: в худшем случае все ключи попадают в одну ячейку и поиск
вырождается в `Θ(m)`.

Средняя длина, однако, не отвечает на вопрос о времени худшего запроса. Его
задает **максимум** длин цепочек, а он считается через
[распределение максимума](random-variables.md#435-функции-от-случайных-величин)
и оказывается заметно больше среднего:

| Схема размещения `n` ключей в `n` ячейках | Ожидаемый максимум |
| --- | --- |
| Случайная ячейка | `Θ(log n / log log n)` |
| Из двух случайных - менее загруженная | `Θ(log log n)` |

Второй результат известен как **выигрыш от двух вариантов**: один
дополнительный запрос уменьшает максимальную нагрузку экспоненциально. Тот же
прием используют балансировщики нагрузки, выбирая наименее загруженный из
двух случайных серверов вместо полного опроса.

### 4.7.4 Рандомизированная быстрая сортировка

Опорный элемент выбирается случайно. Оценивается ожидаемое число сравнений.

Пусть `z₁ < z₂ < ... < zₙ` - элементы в отсортированном порядке, `X_ij` -
индикатор события «`zᵢ` и `zⱼ` сравнивались». Общее число сравнений равно
сумме индикаторов.

**Ключевое наблюдение.** Элементы `zᵢ` и `zⱼ` сравниваются тогда и только
тогда, когда первым опорным среди `zᵢ, ..., zⱼ` окажется один из них. Если
первым выбран промежуточный элемент, то `zᵢ` и `zⱼ` попадают в разные части
и больше не встретятся.

Среди `j − i + 1` элементов отрезка опорный равновероятен, подходят два, и

```
   P(X_ij = 1) = 2 / (j − i + 1)
```

По линейности - без всякого учета зависимости между индикаторами:

```
   E(сравнений) = Σᵢ Σ_{j>i} 2/(j − i + 1)
                = 2·(n + 1)·(Hₙ − 1) − 2·(n − 1)
                = 2n·ln n + O(n) ≈ 1.39 · n·log₂ n
```

Асимптотическая константа `1.39` достигается **медленно**: вычитаемое
слагаемое порядка `n` остается заметным при любых практических размерах.

| `n` | Точное значение | `2n·ln n` | Константа при `n·log₂ n` |
| --- | --- | --- | --- |
| `10³` | 10 986 | 13 816 | 1.10 |
| `10⁶` | 24 785 482 | 27 631 021 | 1.24 |
| `10⁹` | `3.86 · 10¹⁰` | `4.14 · 10¹⁰` | 1.29 |

Для оценок на конкретных данных следует пользоваться точной формулой, а `1.39`
понимать как предел. Даже с поправкой вывод сохраняется: рандомизированная
быстрая сортировка проигрывает сортировкам с гарантированной оценкой
`n log₂ n` лишь десятки процентов сравнений и выигрывает на локальности
обращений к памяти.

**Смысл рандомизации.** Худший случай `Θ(n²)` никуда не исчезает; исчезает
возможность его **вызвать**. При детерминированном выборе опорного элемента
вход, приводящий к квадратичному времени, строится противником по коду
алгоритма. При случайном выборе распределение времени не зависит от входа, и
вероятность заметно превысить среднее исчезающе мала. Это общее свойство
рандомизации: предположение переносится со входных данных на монету.

Реализация и другие сортировки разобраны в
[направлении алгоритмов](../../../algorithms/docs/sprint-3/sorting.md).

### 4.7.5 Метод Монте-Карло, алгоритмы Лас-Вегаса и Монте-Карло

Рандомизированные алгоритмы делятся на два класса по тому, чем они
расплачиваются за случайность.

| Класс | Ответ | Время работы | Пример |
| --- | --- | --- | --- |
| Лас-Вегас | всегда верный | случайное | рандомизированный quicksort |
| Монте-Карло | верный с вероятностью `1 − p` | ограничено | тест Миллера-Рабина |

Классы взаимно сводимы: остановка алгоритма Лас-Вегаса по таймауту дает
алгоритм Монте-Карло, а повторный запуск алгоритма Монте-Карло с проверкой
ответа - алгоритм Лас-Вегаса.

**Усиление надежности.** Если ошибка односторонняя и независима между
запусками, `k` повторов снижают вероятность ошибки до `p^k`:

```
   Тест Миллера-Рабина: одно основание уличает составное число
   с вероятностью не менее 3/4

   k раундов:  P(ошибки) ≤ 4^(−k)
   k = 40:     P(ошибки) ≤ 10⁻²⁴
```

Вероятность ошибки становится ниже вероятности аппаратного сбоя, что и делает
вероятностные тесты простоты практическим стандартом.

**Метод Монте-Карло для вычислений.** Искомая величина представляется как
ожидание, после чего оценивается выборочным средним. Оценка числа `π`:

```
   Точка бросается наудачу в квадрат [0,1]²;
   доля попавших в четверть круга сходится к π/4

   π ≈ 4 · (число попаданий) / N
```

Точность подчиняется
[центральной предельной теореме](limit-theorems.md#464-центральная-предельная-теорема):
погрешность имеет порядок `σ/√N`.

```
   N = 10⁴:   погрешность ≈ 0.016
   N = 10⁶:   погрешность ≈ 0.0016
   N = 10⁸:   погрешность ≈ 0.00016
```

Убывание как `1/√N` делает метод непригодным для задач малой размерности, где
детерминированные квадратуры точнее на порядки. Преимущество Монте-Карло в
другом: погрешность не зависит от **размерности**, поэтому для интегралов по
пространствам высокой размерности альтернативы ему практически нет.

### Типичные ошибки

1. **Порог дней рождения считают линейным по `n`.** Совпадение появляется
   после `≈ 1.177√n` выборок; для 32-битного хеша это около 77 тысяч
   объектов, а не миллиарды.
2. **Ожидаемое время рандомизированного quicksort принимают за худший
   случай.** Худший случай остается `Θ(n²)`, мала лишь его вероятность.
3. **Смешивают анализ в среднем и рандомизацию.** Первый предполагает
   распределение на входах и уязвим к неудачным данным; вторая делает
   предположение о собственной монете и от входа не зависит.
4. **Считают, что покрытие всех `n` вариантов требует `≈ n` проб.** Ответ
   `n·ln n`: для `n = 1000` около 7500 вместо 1000.
5. **Из ожидаемой длины цепочки `α` заключают, что все цепочки коротки.**
   Максимальная длина при `m = n` имеет порядок `log n / log log n`.
6. **Ожидают, что точность Монте-Карло растет линейно с числом опытов.**
   Погрешность убывает как `1/√N`.
7. **Усиление надежности применяют к двусторонней ошибке.** Возведение в
   степень `p^k` справедливо для односторонней ошибки при независимых
   запусках; в общем случае требуется голосование по большинству.
